# Phase 70 — UI Design Contract

> Visual and interaction contract for the File Tray Convert Button (D-01..D-06). Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Extends Phase 34's Quick Action Destination Picker (`34-UI-SPEC.md`) directly** — this is not a new surface, it is a 4th button added to an existing 3-button row, plus a second-step row inside the SAME card. Everything not called out below (shell chrome, `islandFill` material, corner radii, 420pt card width, camera clearance, button-chip anatomy, hover/scale mechanics, no-confirmation-discard convention) is unchanged from `34-UI-SPEC.md` and restated here only where this phase's own decisions (CONTEXT.md D-01..D-06) require a delta.

**Platform note:** Islet is a native macOS SwiftUI app — the shadcn/web-registry gate does not apply (no `components.json`, no Tailwind, no npm-based component library). All values below are SwiftUI points (pt), following this project's established hand-tuned-named-constant convention. No reference screenshot of Islet's own 4-button row exists — the Droppy reference screenshot (`70-CONTEXT.md` §Specifics) confirms only the general "4 equal-width tiles in a row" layout pattern, not Islet's specific icon/label choices, which stay this project's own vocabulary (Drop/AirDrop/Mail unchanged, Convert new).

## Spacing Scale

No new spacing values. Reuses `34-UI-SPEC.md`'s tokens exactly:

| Token | Value | Usage |
|-------|-------|-------|
| sm | 8pt | Button chip's internal icon→label gap; internal vertical padding — unchanged |
| md | 16pt | Gap between chips in a row (`HStack(spacing: 16)`); outer content horizontal inset; bottom inset below the button row — unchanged, now also governs the gap between format tiles |
| — | 42pt | `cameraClearance` — grandfathered, unchanged |

**Geometry confirmation (this phase's own arithmetic, RESEARCH.md):** 4 buttons at the existing fixed `quickActionButtonWidth` (130pt) + 3×16pt gaps = 568pt, inside the 602pt available content width (650pt Tray-card width − 2×24pt padding — this card family reuses the Tray card width, not the 420pt `expandedSize.width` Phase 34 originally sized against; confirm the actual current card width constant at implementation time and re-run this arithmetic if it differs). No card resize needed for either the 4-button row (Drop/AirDrop/Mail/Convert) or the 4-tile format row (JPG/PNG/HEIC/TIFF) — both are 4-item rows using the same per-item width, so `quickActionPickerContentHeight` does NOT change between the two steps (D-01: "No new card geometry/height").

## Typography

No new sizes or weights. Reuses `34-UI-SPEC.md`'s single role exactly:

| Role | Size | Weight | Usage |
|------|------|--------|-------|
| Button/tile label | 11pt | semibold (600) | "Drop" / "AirDrop" / "Mail" / "Convert" chip labels AND "JPG" / "PNG" / "HEIC" / "TIFF" format-tile labels — same role, same styling, no distinction between the two rows' typography |

**Icon point sizes (SF Symbol, not a text role):**
- Convert button icon: 22pt SF Symbol in the same fixed `.frame(width: 22, height: 22)` box as Drop/AirDrop/Mail (Phase 34 Pitfall 9 fix applies identically — do not regress to intrinsic-bounds sizing). Icon: `arrow.triangle.2.circlepath` (closest standard SF Symbol match to the reference screenshot's circular refresh-arrows concept).
- Format-tile icon: **one single shared icon across all 4 tiles** — `photo` — same 22pt fixed-frame treatment. Do NOT invent a distinct icon per format (JPG/PNG/HEIC/TIFF are file-format labels, not concepts with dedicated SF Symbol glyphs); the label text alone differentiates the 4 tiles. This is the resolved answer to RESEARCH.md Open Question 1.

**2-weight budget (unchanged):** regular (400) + semibold (600) — this phase introduces no new weight.

## Color

No new palette. Reuses `34-UI-SPEC.md`'s color contract exactly, including its idle/drag-hover/disabled fill table:

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | Existing Phase 25 `islandFill` gradient | Card background — unchanged |
| Secondary (30%) | `.secondary` | Not actively used inside this picker (unchanged from Phase 34) |
| Accent (10%) | none introduced | Convert and the format tiles stay equal-weight with Drop/AirDrop/Mail — no button reads as "primary" |
| Destructive | not applicable | No destructive action in this phase — conversion produces a NEW file, never overwrites/deletes the original (D-04) |

**Idle vs. drag-hover vs. disabled fill (reused verbatim from Phase 34 D-11/D-09):**

| State | Chip fill | Scale | Icon+label opacity |
|-------|-----------|-------|----------------------|
| Idle (enabled) | `Color.white.opacity(0.12)` | 1.0 | 1.0 |
| Drag-hovered | `Color.white.opacity(0.22)` | 1.04 | 1.0 |
| Disabled | `Color.white.opacity(0.06)` | 1.0 (no hover response) | 0.3 |

**This phase's specific application of the disabled state (D-05):** Convert renders in the **disabled** row above whenever `pendingDrop.items` contains ANY item that is not an image (`!isImageFile(item.originalURL)` for at least one item) — computed fresh, inline, on every render directly from `pendingDrop.items` (RESEARCH.md Pattern 3), never from a stored/threaded `Bool` the way `airDropAvailable`/`mailAvailable` were (confirmed dead — see D-06 below). Convert is enabled only when `pendingDrop.items.allSatisfy { isImageFile($0.originalURL) }`. A disabled Convert chip is never a valid drop target at release (D-06 controller-gate fix — see Layout & Interaction Contract §4).

**Accent reserved for:** unchanged from Phase 34 — no new reserved tint. Format tiles, like the main row, stay equal-weight; only the transient drag-hover highlight differentiates whichever tile is under the pointer.

## Layout & Interaction Contract

*(Supplementary section — this phase adds a 4th chip to an existing row plus a second render/hit-test stage inside the same card. Executor: read this before touching code, and read `34-UI-SPEC.md` §5-7 first — this section only states the delta.)*

### 1. Main row — add Convert as the 4th chip

```swift
private func quickActionButtonRow(_ pending: PendingDrop) -> some View {
    HStack(spacing: 16) {
        quickActionButton(icon: "tray.and.arrow.down.fill", label: "Drop", enabled: true,
                           isHovered: hoveredQuickActionButtonIndex == 0)
        quickActionButton(icon: "personalhotspot", label: "AirDrop", enabled: airDropAvailable,
                           isHovered: hoveredQuickActionButtonIndex == 1)
        quickActionButton(icon: "envelope.fill", label: "Mail", enabled: mailAvailable,
                           isHovered: hoveredQuickActionButtonIndex == 2)
        quickActionButton(icon: "arrow.triangle.2.circlepath", label: "Convert",
                           enabled: pending.items.allSatisfy { isImageFile($0.originalURL) },
                           isHovered: hoveredQuickActionButtonIndex == 3)
    }
}
```
`quickActionButton(icon:label:enabled:isHovered:)` itself is reused with ZERO changes — its disabled-dim (D-09) and hover-scale (D-11) behavior already produce the correct visual for Convert with no new view code.

### 2. Second step — format-tile row replaces the main row in-place (D-01)

Same card, same `blobShape` call, same `quickActionPickerContentHeight` — only the row's content swaps:

```swift
private func formatTileRow(_ pending: PendingDrop) -> some View {
    HStack(spacing: 16) {
        ForEach(ImageFormat.allCases.indices, id: \.self) { i in
            let format = ImageFormat.allCases[i]
            quickActionButton(icon: "photo", label: format.label, enabled: true,
                               isHovered: hoveredQuickActionButtonIndex == i)
        }
    }
}
```
Reuses `quickActionButton` verbatim — same fixed 22×22pt icon frame, same 11pt semibold label, same idle/hover fill steps. All 4 format tiles are always enabled (D-02: no per-format availability gating — the enablement gate already happened at the main row's Convert chip).

### 3. Controller-side stage state (new — required by D-01's "second step in the same card")

The controller needs explicit state for which row is currently showing, since this is the first time this component has needed two stages within one card presentation (RESEARCH.md Pitfall 4):

- Introduce a stage flag (e.g. `isShowingConvertFormats: Bool`, controller-owned) that both (a) the view reads to decide which row to render, and (b) `handleDragApproachEnd()`'s hit-test switch reads FIRST, before branching on index — so a release on format-tile index 1 ("PNG") is never misrouted to `handleQuickActionAirDrop()` (index 1 in the main row's mapping).
- `computeQuickActionButtonFrames(card:count:)` (generalized per RESEARCH.md Pattern 4) must be recomputed for the CURRENT stage's row on every stage transition — not just once per `positionAndShow()` — since the main row and the format row occupy the same screen rect but map different indices to different actions.

### 4. D-06 controller-gate fix — mandatory, ships in this same phase

Confirmed via codebase grep (RESEARCH.md Pattern 3/Pitfall 3): `airDropAvailable`/`mailAvailable` are rendered as dimmed by the view today but have **no matching gate** in `handleDragApproachEnd()` — a release on a dimmed AirDrop/Mail chip still fires its handler. This phase must add that gate for ALL 4 main-row buttons (not just Convert), since Convert is the first `enabled` flag that is ever actually `false` in real use and will be the first to surface this bug live. Concretely: the hit-test switch must check the SAME `enabled` condition the view used to render dim state before dispatching a handler — a release over a disabled chip (main row OR format row) behaves exactly like D-13's "released inside the card but not on a button" (discard, no action), never a silent handler call.

### 5. What this phase does NOT touch

No new card width, no new card height, no new corner radii, no new font size/weight, no new fill opacity value, no new hover-scale value — every visual constant is reused verbatim from `34-UI-SPEC.md`. The only new visual elements are one new icon (`arrow.triangle.2.circlepath` for Convert) and one shared icon (`photo` for all 4 format tiles), applied through the existing `quickActionButton` component with zero styling changes to that component itself.
