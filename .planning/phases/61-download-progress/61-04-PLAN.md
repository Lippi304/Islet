(D-14 — never replay history); `latency: 0.3` (seconds — coalesces rapid events, well inside SC1's

the callback via `Unmanaged<DownloadMonitor>.fromOpaque(clientInfo!).takeUnretainedValue()` — verify

article or `jgvanwyk/SwiftFileSystemEvents` on GitHub before treating it as final).

Inside the callback, for each index in the batch (`numEvents`, in the given order — FSEvents
preserves within-batch order via `eventIds`, per Pitfall 3): with `kFSEventStreamCreateFlagUseCFTypes`
+ `UseExtendedData` set, `eventPaths` is a `CFArray` of `CFDictionary`, one per event — extract the
path via the `kFSEventStreamEventExtendedDataPathKey` entry and the file ID via
`kFSEventStreamEventExtendedFileIDKey` (a `CFNumber`; convert to `UInt64`, `nil` if absent). Compute
`(path as NSString).deletingLastPathComponent` and SKIP the event entirely unless it exactly equals
the watched Downloads path (Pitfall 1 — filters out writes happening INSIDE a Safari `.download`
bundle's own contents, while still catching the bundle's own top-level create/rename since THAT
event's parent IS the Downloads root).

For surviving events, maintain a `private var pendingRenamesByFileID: [UInt64: String] = [:]` (a
SEPARATE table from `DownloadCoordinator`'s own `inFlightDownloads` — this one only exists to pair the
two halves of a single `mv`, which per Pitfall 2/3 may arrive in the SAME or in DIFFERENT callback
batches). Classify each surviving event by its flags:
- Flags contain `kFSEventStreamEventFlagItemRenamed` AND `FileManager.default.fileExists(atPath: path)`
  is `false` (the "moved away" half): if `fileID != nil`, store `pendingRenamesByFileID[fileID!] = path`
  and do NOT call `onEvent` yet (waiting for the "moved to" half). If `fileID == nil` (extended data
  unavailable for this event — Assumption A3's "cosmetic, not crash-level" degrade path), call
  `onEvent(DownloadReading(path: path, kind: .removed, fileID: nil, renamedTo: nil))` instead —
  correlation isn't possible without a file ID, so treat it as a plain removal (the coordinator's own
  D-08 gate silently ignores it if it was never tracked).
- Flags contain `kFSEventStreamEventFlagItemRenamed` AND `fileExists(atPath: path)` is `true` (the
  "moved to" half): if `fileID != nil` and `pendingRenamesByFileID[fileID!]` has a stored old path,
  call `onEvent(DownloadReading(path: oldPath, kind: .renamed, fileID: fileID, renamedTo: path))` and
  remove that entry. If no matching pending entry exists (the "moved away" half hasn't arrived, or
  `fileID == nil`), call `onEvent(DownloadReading(path: path, kind: .created, fileID: fileID, renamedTo: nil))`
  instead — degrading an unpaired rename-to event to a plain create is safe: the coordinator's D-08
  suffix guard will simply ignore it (a final, non-temp filename never matches the known suffixes).
- Flags contain `kFSEventStreamEventFlagItemCreated` (no `ItemRenamed`) and `fileExists(atPath: path)`
  is `true`: call `onEvent(DownloadReading(path: path, kind: .created, fileID: fileID, renamedTo: nil))`.
- Flags contain `kFSEventStreamEventFlagItemRemoved` (no `ItemRenamed`) and `fileExists(atPath: path)`
  is `false`: call `onEvent(DownloadReading(path: path, kind: .removed, fileID: fileID, renamedTo: nil))`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| `~/Downloads` filesystem (any local process, including a malicious/adversarial download) → `DownloadMonitor`'s FSEvents callback | The monitor only reads paths/flags/file IDs supplied by the OS's own FSEvents API — it never opens, reads the contents of, or follows any path found (read-only metadata only, no `Data(contentsOf:)` call anywhere in this plan). |
| FSEvents C callback → Swift `DownloadMonitor` instance | The `Unmanaged.passUnretained`/`fromOpaque` bridge must not create a retain cycle or a use-after-free — mirrors every existing monitor's (`PowerSourceMonitor`, `CapsLockMonitor`) established teardown discipline. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-61-08 | Tampering / Information Disclosure | Symlink or path-traversal inside a downloaded `.download` bundle or any other `~/Downloads` entry | mitigate | This plan only ever calls `FileManager.default.fileExists(atPath:)` (a read-only existence check) on FSEvents-reported paths — never `Data(contentsOf:)`, never opens/follows/copies any file contents. No new file-read surface is introduced. |
| T-61-09 | Denial of Service | A flood of rapid FSEvents (many files dropped/renamed at once, or a malicious script hammering `~/Downloads`) | mitigate | `FSEventStreamCreate`'s own 0.3s latency coalesces rapid events into batches; `DownloadCoordinator`'s `TransientQueue` interaction stays bounded via the existing `maxDepth = 2` (T-06-09 precedent) regardless of how many raw events arrive. |
| T-61-10 | Elevation of Privilege / Use-After-Free | `Unmanaged.passUnretained(self)` C callback bridging outliving the `DownloadMonitor` instance | mitigate | `stop()` calls `FSEventStreamStop`/`Invalidate`/`Release` before the instance can be deallocated, mirroring `PowerSourceMonitor`/`CapsLockMonitor`'s identical, already-proven teardown discipline; `NotchWindowController.deinit` calls `stop()` explicitly (never relies on ARC alone). |
| T-61-11 | Tampering (npm/pip/cargo) | N/A | accept | Zero new external packages this phase — `CoreServices`/`Foundation` ship with the macOS SDK already linked by this project |
</threat_model>
