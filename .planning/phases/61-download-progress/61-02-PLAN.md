<objective>
Build the stateful per-file coordinator that turns `DownloadMonitor`'s (Plan 61-04) raw
create/rename/remove readings into the queue-facing `.downloadProgress(DownloadActivity)` transient,
resolving D-05/D-06's multi-instance-identity requirement (mirrors `DeviceCoordinator`'s
address-keyed side table, per PATTERNS.md) and RESEARCH.md's Open Question 1 (a completing
download's done state is a plain `enqueue` when another download is still active, or an in-place
`replaceHead` when it was the last one in flight — never a coordinator-side promoted re-check).

bookkeeping (per-tempPath tracking, the never-self-elapsing `.inProgress` head's "who gets to
replace it" question) into its own focused, thoroughly-unit-tested file before Plan 61-04 wires a
real FSEvents monitor to it.
Output: `DownloadCoordinator.swift` (new), `IsletTests/DownloadCoordinatorTests.swift` (new, mirrors
`DeviceCoordinatorTests.swift`'s "no fakes, wire closures to a real `var q = TransientQueue()`"
convention).

Create `Islet/Notch/DownloadCoordinator.swift`: `import Foundation` only. Define
`@MainActor final class DownloadCoordinator: ActivityCoordinator { typealias Reading = DownloadReading ... }`.

Private state: `private struct InFlightDownload: Equatable { let tempPath: String; let fileID: UInt64?; let startedAt: Date }`
and `private var inFlightDownloads: [String: InFlightDownload] = [:]` keyed by `tempPath` — mirrors
`DeviceCoordinator.pendingDeviceBatteryPolls`'s per-identity side-table discipline, but keyed
differently (by path, since each temp file IS its own logical download per D-06, not by a shared
device address).

Four closures (SMALLER than Device's 6 — no battery-poll/updateHead-for-scrub equivalent needed):
`private let queueHead: () -> ActiveTransient?`, `private let enqueue: (ActiveTransient) -> Bool`,
`private let replaceHead: (ActiveTransient) -> Void`, `private let presentTransientChange: () -> Void`.
`init(queueHead:enqueue:replaceHead:presentTransientChange:)` stores all four (mirrors
DeviceCoordinator's init shape exactly, just fewer parameters). Document that `enqueue` is expected to
already carry the caller's own preempt-if-Focus-else-enqueue logic (mirrors `DeviceCoordinator`'s own
`enqueue` closure contract — this coordinator never inspects `queueHead()` to decide Focus-preemption
itself) and that `replaceHead` is expected to do `transientQueue.updateHead(t)` PLUS re-arm the shared
~3s dismiss timer (mirrors `handleOSDKeyPress`'s in-place branch) — Plan 61-04 wires both.

`func handle(_ reading: DownloadReading) { handle(reading, now: Date()) }` and
`func handle(_ reading: DownloadReading, now: Date)` (the testable overload, mirrors
`DeviceCoordinator`'s `now:` threading so `startedAt` timestamps are deterministic in tests — no
`Date()` call anywhere inside the `now:` overload's own body).

Inside `handle(_:now:)`, switch on `reading.kind`:
- `.created`: `guard isDownloadTempFile(path: reading.path) else { return }` (D-08). Store
  `inFlightDownloads[reading.path] = InFlightDownload(tempPath: reading.path, fileID: reading.fileID, startedAt: now)`.
  Call `if enqueue(.downloadProgress(.inProgress)) { presentTransientChange() }` — D-05's "shows only
  the most recently started one" falls out for free here: every in-progress download renders the SAME
  generic value (D-09), so `TransientQueue`'s own equality-based dedup naturally collapses a second
  concurrent download into a no-op re-enqueue attempt with zero visual change.
- `.renamed`: `guard inFlightDownloads.removeValue(forKey: reading.path) != nil else { return }` (D-08
  re-applied — an untracked rename is irrelevant). `guard let finalPath = reading.renamedTo else { return }`.
  Compute `let doneActivity = ActiveTransient.downloadProgress(.done(filename: downloadFilename(fromPath: finalPath)))`.
  If `inFlightDownloads.isEmpty` (this WAS the last tracked download): `if case .downloadProgress = queueHead() { replaceHead(doneActivity) } else if enqueue(doneActivity) { presentTransientChange() }`
  — the `if case .downloadProgress = queueHead()` check matches EITHER inner case (mirrors
  `handleOSDKeyPress`'s `if case .osd = transientQueue.head` outer-case-only match), covering both "the
  standing head is still the stale `.inProgress`" and "the standing head is already a DIFFERENT
  download's still-showing `.done` splash" — both cases get replaced in place. If a `.downloadProgress`
  head is NOT currently standing (e.g. Charging preempted it, or nothing has ever shown), fall back to
  plain `enqueue` (D-05's "fires independently later" — queues behind whatever stands, or becomes head
  if nothing does). If `inFlightDownloads` is NOT empty (another download still in flight): `_ = enqueue(doneActivity)`
  unconditionally — D-05's literal "the older download's own done state still fires independently
  later" — queue behind the current `.inProgress` head, never replace it while a real download is
  still active.
- `.removed`: `inFlightDownloads.removeValue(forKey: reading.path)` — D-15, no `enqueue`/`replaceHead`
  call at all, regardless of whether the path was tracked.

`func activityPromoted() {}` — empty body with a doc comment explaining WHY (RESEARCH.md Open
Question 1's resolution, cited above): unlike `DeviceCoordinator`'s battery-poll follow-up, Download
has no deferred side-effect that needs re-checking once a different transient is promoted to head —
a completing download's own `.done` transition is fully handled inside `handle(_:now:)`'s `.renamed`
branch above, via plain `TransientQueue` enqueue/advance mechanics. The empty body still satisfies
`ActivityCoordinator`'s protocol requirement.

`func reset() { inFlightDownloads.removeAll() }` — mirrors `DeviceCoordinator.reset()`'s exact
one-line shape and doc-comment convention (clearing an in-flight/pending side table on Settings
toggle-off). Ship this HERE, alongside the table it clears, rather than leaving it for Plan 61-04 to
add cross-plan — Plan 61-04's `handleSettingsChanged` toggle-off branch calls this method directly.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| `DownloadReading` (untrusted path/filename, per Plan 61-01) → `DownloadCoordinator`'s in-flight table | The coordinator only ever uses `reading.path`/`.renamedTo` as dictionary KEYS and as input to the pure `isDownloadTempFile`/`downloadFilename` functions — never interpolated into a format string, shell command, or further filesystem path-construction call. |
| Repeated/flood filesystem events → `inFlightDownloads` growth | A malicious or misbehaving process could theoretically create many temp-suffixed files in `~/Downloads` in rapid succession — bounded resource-exhaustion risk, see mitigation below. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-61-03 | Tampering (of displayed data) | `downloadFilename(fromPath:)`'s output, stored transiently in `inFlightDownloads`/passed to `enqueue` | accept (this plan) / mitigate (Plan 61-03) | Never used for anything beyond a dictionary key and a value carried through to the UI layer, which applies the actual render-safety mitigation (`.lineLimit(1)` + `.truncationMode(.middle)`). |
| T-61-04 | Denial of Service | `inFlightDownloads` unbounded growth from many rapid/never-completing temp files | accept | RESEARCH.md's own Open Question 2 recommendation: entries are removed on BOTH success (`.renamed`) and cancellation (`.removed`), so the dict is self-cleaning under realistic Downloads-folder usage; the VISIBLE queue itself stays bounded regardless via `TransientQueue.maxDepth = 2` (existing T-06-09 precedent), so even an unbounded backing dict cannot flood the collapsed HUD itself. |
| T-61-05 | Tampering (npm/pip/cargo) | N/A | accept | Zero new external packages this phase |
