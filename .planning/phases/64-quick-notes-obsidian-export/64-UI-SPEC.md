# Phase 64 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This is a **menu-bar-only feature** (D-13, locked). There is zero notch/`IslandResolver` UI in this phase — the entire visual surface is: (1) one new `NSMenuItem` ("New Note…"), (2) one new `NSPopover` (input + recent-notes list), (3) one Settings card's `onOptionsTap` wiring (card itself already shipped in Phase 59). This contract covers those three surfaces only.

## Spacing Scale

This is brand-new SwiftUI content inside an `NSPopover` (per D-04's recommended shape — input + list in one popover, not `NSMenuItem` rows) — unlike `ClipboardRowView`, it is not constrained by `NSMenuItem.view`'s fixed-frame quirk, so it follows a clean 4pt-multiple scale rather than that view's odd 14pt/22pt geometry.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4pt | Icon-to-text gaps, timestamp-to-note-text gap in a recent-notes row |
| sm | 8pt | Compact spacing: submit-button internal padding, row internal vertical padding |
| md | 16pt | Popover content padding (edges), gap between the input area and the recent-notes list |
| lg | 24pt | not used in this phase's minimal surface |

Exceptions:
- If D-04 is later revised to the `NSMenu`-submenu-of-`NSHostingView`-rows shape (the alternative CONTEXT.md left open), rows MUST instead match `ClipboardRowView`'s exact existing geometry (`rowWidth = 260`, height `22pt`, horizontal padding `14pt`, internal `HStack` spacing `6pt`) — do not invent new row geometry for a second, inconsistent menu-row shape in the same app.
- Popover fixed width: **280pt** (20pt wider than `ClipboardRowView.rowWidth` to give the multi-line `TextEditor` breathing room) — chosen, not researched; adjust on-device if text wrapping looks cramped.
- Recent-notes list per-row height: **not fixed** (unlike the 22pt Clipboard row) — a note can wrap to multiple lines in its preview; each row sizes to content with `sm` (8pt) vertical padding.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Note input (`TextEditor`) | 13pt | regular (400) | 1.4 (multi-line capture, matches this codebase's `ClipboardRowView` body-text size) |
| Recent-note row text | 13pt | regular (400) | 1.4 (notes can wrap to 2-3 lines; generous line height keeps wrapped lines legible) |
| Recent-note row timestamp | 11pt | regular (400), `.secondary` foreground | 1.2 (single line, matches `ActivityCard`'s existing 11pt description size) |
| Empty-state / error-banner text | 11pt | regular (400), `.secondary` (empty state) or destructive (error banner) | 1.3 |

Exactly 2 weights declared project-wide for this phase: **regular (400)** for all body/list/meta text, **semibold (600)** reserved only for the submit button's label (matches `ActivityCard`'s existing semibold-for-title convention) — no other element in this phase uses semibold.

## Color

Native macOS apps use semantic system colors (not literal hex) so the UI adapts automatically to Light/Dark Mode and the user's accent-color preference — this is the established convention in `ActivityCard.swift`/`ClipboardRowView` and is followed here rather than hardcoding hex values.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `NSPopover`'s default system content background (standard vibrant popover material — no override) | The popover's own background, top-to-bottom |
| Secondary (30%) | `Color(nsColor: .controlBackgroundColor)` | Recent-notes list container background — matches `ActivityCard`'s existing card-background token exactly |
| Accent (10%) | `Color.accentColor` | Reserved for: (1) the "Save Note" submit button's prominent/tinted state only. Nothing else in this phase uses accent color. |
| Destructive | `Color.red` (`NSColor.systemRed` equivalent) | Reserved for: (1) the per-row delete control (hover-revealed trash icon) on a recent-note row, (2) the inline write/path-failure error banner's text and leading icon. Nothing else uses red. |

Accent reserved for: the submit button only — never the delete icon, never the empty-state icon, never row hover highlight (hover uses `Color.primary.opacity(0.08)`, matching `ClipboardRowView`'s existing hover treatment exactly).

## Copywriting Contract

| Element | Copy |
|---------|------|
| Menu item (locked, D-01) | `New Note…` |
| Primary CTA (submit button) | `Save Note` |
| Empty state heading | `No notes yet` |
| Empty state body | `Notes you capture here are also appended to your Obsidian vault file.` |
| Vault-not-configured state (D-11: path checked on popover open) | Heading: `Vault folder not set` / Body: `Choose an Obsidian vault folder in Settings to start capturing notes.` — input is disabled while this state shows |
| Error state (D-12: write failure — inline banner, per RESEARCH.md Open Question 2's recommended single generic message) | `Couldn't save — check your vault folder in Settings.` Typed text remains in the input field untouched; nothing is added to the recent-notes list (D-12 locked rule). |
| Destructive action: per-row delete (D-17) | No modal confirmation. Single click on the hover-revealed trash icon deletes immediately — this only removes the local list entry; the vault `.md` file is never touched (D-17), so the action is low-stakes and reversible in effect (the note still exists in the vault). Matches this codebase's existing low-friction single-click pattern (Clipboard row restore-on-click) rather than Clipboard's separate high-stakes `confirmDeleteAllHistory` modal, which this phase does not have an equivalent of (no "Delete All" — D-17). |

## Interaction Notes (non-template, phase-specific — read before implementing)

- **Popover-open behavior (D-03, resolved per RESEARCH.md's recommendation):** the popover **stays open on submit** — input field clears, the recent-notes list updates in place, focus returns to the (now-empty) `TextEditor`. It does NOT auto-close on a successful save. `.behavior = .transient` still auto-closes on outside click / Escape (baseline dismiss), which is unrelated to the submit path.
- **Recent-notes list location (D-04, resolved per RESEARCH.md's primary recommendation):** the list renders **inside the same popover**, below the input (`TextEditor` on top, `ScrollView` of notes below), NOT as a separate `NSMenu` submenu of `NSHostingView` rows. One `New Note…` menu item is the only entry point — no separate `Quick Notes…` anchor item.
- **Vault filename (D-08):** fixed at `Islet Notes.md`.
- **Keyboard focus (Pitfall 10 — genuinely unverified, flag for on-device spike):** the popover's `TextEditor` must receive real first-responder status immediately on open with zero extra click — call `window?.makeFirstResponder(...)` right after `show(relativeTo:of:preferredEdge:)`, per RESEARCH.md Pattern 1. Do not treat this as settled until confirmed on-device; if focus never lands reliably, this UI-SPEC's popover-based capture surface needs re-review, not a silent fallback.
- **Row structure (recent-notes list):** each row shows the timestamp (`11pt`, `.secondary`) inline before the note's first line of text (`13pt`, regular), remaining lines wrap below at the same `13pt` size — most-recent-first (D-16: clicking a row does nothing, it's pure display). Hovering a row reveals the destructive-red delete icon at the trailing edge (mirrors `ClipboardRowView`'s existing `NSTrackingArea`-based hover pattern, not SwiftUI `onHover`, per that view's own documented `mouseExited`-reliability fix).
