short, read it directly before writing MeetingMonitor.swift):
```swift
@MainActor
final class CapsLockMonitor {
    private nonisolated(unsafe) var monitorToken: Any?
    private nonisolated(unsafe) var healthCheckTimer: Timer?
    private var lastCapsLockState: Bool?
    private let onChange: (Bool) -> Void
    init(onChange: @escaping (Bool) -> Void) { self.onChange = onChange }
    func start() { guard monitorToken == nil else { return }; ... }
    nonisolated func stop() { ... NSEvent.removeMonitor(token) ... }
    deinit { /* empty — owner's deinit calls stop() */ }
}
```
The dedup discipline (`lastCapsLockState`, only calling `onChange` on an ACTUAL transition, not
every tick) is the critical piece `MeetingMonitor` must copy — Plan 63-04's controller handler
depends on `onChange` firing exactly once per real call-start/end to safely call
`transientQueue.preempt(_:)`/`removeAll(where:)` without duplicate-entry risk.

From Islet/Notch/AudioOutputMonitor.swift (the event-driven CoreAudio block-listener pattern):
```swift
let block: AudioObjectPropertyListenerBlock = { [weak self] _, _ in
    DispatchQueue.main.async { [weak self] in
        guard let self else { return }
        self.onDevicesChanged(self.currentDevices())
    }
}
listenerBlock = block
var devicesAddr = AudioObjectPropertyAddress(mSelector: kAudioHardwarePropertyDevices, ...)
AudioObjectAddPropertyListenerBlock(AudioObjectID(kAudioObjectSystemObject), &devicesAddr, nil, block)
```
CRITICAL: `AudioObjectAddPropertyListenerBlock` delivers on a CoreAudio-internal dispatch queue,
NOT main — `@MainActor` on the class does NOT retroactively isolate it. Must hop to
`DispatchQueue.main.async` before touching stored state or calling `onChange`, exactly like this
block does.

From Islet/Notch/MicMuteController.swift (Plan 63-01, already built — REUSE, do not reimplement):
`func defaultInputDeviceID() -> AudioDeviceID?` — call this directly to resolve the input device
the `kAudioDevicePropertyDeviceIsRunningSomewhere` listener targets.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Local process list (NSWorkspace) | `MeetingMonitor` reads other local processes' bundle identifiers — read-only, no cross-process control |
| CoreAudio HAL (input device) | Local system audio state, no network boundary |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-63-03 | Spoofing | MeetingMonitor's bundle-ID matching against `NSWorkspace.runningApplications` | accept | A malicious local process could spoof its `bundleIdentifier` to appear as Zoom/Teams, but this is out of a single-user desktop app's realistic threat model — same disposition as this codebase's existing precedent (no local-process spoofing has ever been treated as in-scope); worst case is a spurious Meeting-HUD display, no data/security impact |
| T-63-04 | Denial of Service | `MeetingMonitor`'s CoreAudio listener/poll-timer lifecycle leaking across repeated Settings toggle-on/off | mitigate | Idempotent `start()`/`stop()` mirroring `CapsLockMonitor` exactly — `stop()` removes the retained `AudioObjectPropertyListenerBlock` (same block reference required by `AudioObjectRemovePropertyListenerBlock`) and invalidates the poll `Timer`/NSWorkspace notification observers so nothing outlives the monitor's owner |
| T-63-05 | Information Disclosure | Console `print` logging in `MeetingMonitorManualSpike.swift` | accept | Manual-spike-only test file, never exercised by `xcodebuild test -scheme Islet` (the CI/regression path) and never shipped in a Release build — no PII logged (only bundle IDs + booleans + timestamps) |
</threat_model>
