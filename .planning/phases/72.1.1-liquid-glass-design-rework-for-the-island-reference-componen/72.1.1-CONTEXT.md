# Phase 72.1.1: Liquid Glass Design Rework for the Island - Context

**Gathered:** 2026-07-31
**Status:** Ready for planning

<domain>
## Phase Boundary

The island's Liquid Glass material (`materialStyle == .liquidGlass`, the current default) gets reworked from today's narrow-rim-only look (Phase 35 D-20a: a thin `LiquidGlassRimRingShape` gets real `.glassEffect()`, everything else stays a solid dark fill) into a fuller glass look across the whole island surface — collapsed pill, expanded island, and every activity wing — driven by a new reference component (`21st.dev/r/suraj-xd/liquid-glass`, a macOS-Dock-icon-style liquid glass effect). The rework also extends the glass look to select elements *inside* the island (buttons/tabs, cards/tiles, OSD bars) and fixes the known transition-flicker bug as part of achieving consistent glass visibility across all states. Roadmap entry landed with `Requirements: TBD` and goal `[Urgent work - to be planned]` — this discussion is what defines the actual scope.

</domain>

<decisions>
## Implementation Decisions

### Effect Coverage
- **D-01:** The glass effect is **not confined to a rim** anymore. It follows the existing top-black → bottom-transparent gradient direction (`gradientMaterial`, unchanged direction from Phase 25/35 D-02) across the **whole island surface**, made glossier/more glass-like throughout — not just at the edge. This supersedes Phase 35 D-20a's rim-only scope for this phase's purposes (D-20a's rim mechanism may still inform *how* it's built, but the visible result is no longer rim-limited).
- **D-02:** Readability of text/icons **takes priority** over maximum glass intensity if the two conflict — same precedence Phase 35 already established (D-15: center darkness precedent) and consistent with every prior material decision in this project. If more glass coverage risks legibility, dial back the glass rather than the readability.

### Visibility Across States (supersedes deferred transition bug)
- **D-03:** The glass look must be **consistently present in every island state** — collapsed pill, mid collapse↔expand animation, the small/compact expanded state, and the full expanded state. Not just the settled/idle look.
- **D-04:** This explicitly **resolves the known deferred bug** documented in `.planning/debug/resolved/liquid-glass-black-during-transition.md` (glass drops to flat black during collapse↔expand morph and tab switches) — that bug is now in-scope for this phase, not still deferred. The `GlassEffectContainer`/`.glassEffectID` approach mentioned as "attempted and reverted" in that doc is a known-bad prior attempt (caused the whole island to frost permanently) — do not repeat it as-is; research a different mechanism for continuous glass rendering during identity/geometry changes.
- **D-05:** No live mouse/pointer-driven reactivity (unlike the real macOS Dock's cursor-follow behavior). "Dynamic" in this phase means *state-driven* (glass present through every animation/state transition), not *pointer-driven*. Explicitly ruled out — do not build cursor-tracking distortion.

### Scope: Island Shell + Selected Inner Elements
- **D-06:** The glass look extends beyond the outer island shell to specific elements **inside** the island:
  - Buttons/icons: Quick Action buttons, view-switcher tabs
  - Cards/tiles: Calendar event cards, the Weather widget, Tray file tiles
  - OSD bars/sliders: the Volume and Brightness bars (`OSDLevelBar`, just redesigned in Phase 72.1)
- **D-07 (interaction with Phase 72.1):** OSD bar glass treatment must **layer on top of, not replace**, Phase 72.1's locked opacity-ramp mechanic (D-01/D-02/D-03 in `72.1-CONTEXT.md`: fill brightness/opacity scales with fraction filled, colors stay fixed green/orange, no accent tint). The glass look is an additional visual layer on the bar, not a redesign of the fill-opacity behavior that phase just shipped.
- **D-08:** No other inner elements (e.g., Settings window content, onboarding) are in scope unless research finds they share a code path with one of the D-06 elements. Settings' existing calmer glass variant (Phase 35 D-08/D-09) is not explicitly touched by this discussion — flag to the user during planning if it turns out to need matching changes.

### Claude's Discretion
- Exact technical mechanism for full-surface glass (native `.glassEffect()` scaled up vs. a masked/composited approach vs. reworking the legacy shader stack) — planner/researcher's call based on what actually achieves D-01 without breaking D-02.
- Exact fix mechanism for the transition-flicker bug (D-04) — research required; the previously-reverted `GlassEffectContainer` approach is ruled out as-is, but variations or entirely different mechanisms are open.
- Order/sequencing of which D-06 elements are tackled first if this needs to split across multiple plans (island shell is very likely the foundational piece other elements build on).
- Whether "glossier" (D-01) is achieved via increased specular highlight, higher blur-clarity, brighter rim-light stroke, or some combination — pick whatever reads best on-device, subject to on-device UAT given this project's history with Liquid Glass tuning (Phase 35 needed 5 UAT rounds).

</decisions>

## Existing Code Insights

### Reusable Assets
- `LiquidGlassRimRingShape` (`NotchPillView.swift:718`) — existing `Shape` conformance for confining `.glassEffect()` to a region; the mechanism (a `Shape` passed to `.glassEffect(_:in:)`) generalizes if full coverage needs a different (larger, or full-shape) region rather than a ring.
- `liquidGlassOpacityShader`/`liquidGlassEdgeOpacity` Metal colorEffect — existing single source-of-truth falloff function, reusable if the legacy shader stack needs reviving/extending for full-surface coverage.
- Wing Tuner `@AppStorage`/NSMenu 3-file DEBUG tuner pattern (established across Phase 71 SHAPE-03, Phase 72.1 D-05) — directly reusable if this phase's new glass parameters (opacity, glossiness, blur) need on-device tuning, which prior Liquid Glass work strongly suggests they will.

### Established Patterns
- Every visual/geometry-touching phase in this project needs multiple on-device UAT rounds before shipping (Phase 35 alone needed 5 full revision rounds). Budget planning and execution time accordingly — do not expect first-attempt approval.
- "Propose a value → live-tune on hardware via a DEBUG menu → bake in with a comment" convention (same as Phase 71/72.1) applies to any new glass tuning constants.
- `matchedGeometryEffect` continuity constraint: new material work MUST apply as a modifier at existing fill call sites, never as a new sibling/wrapper view (this project broke `matchedGeometryEffect` continuity once already doing exactly this class of change — WR-02, referenced in 35-CONTEXT.md).

### Integration Points
- `islandFill` + `liquidGlassEffectLayer` is the single shared seam for the outer shell (4 call sites) — the natural first-plan target.
- Each D-06 inner element (Quick Action buttons, switcher tabs, Calendar cards, Weather widget, Tray tiles, OSD bars) has its own separate render location in `NotchPillView.swift` — these are NOT wired through the shared `islandFill` seam today, so extending glass to them is genuinely separate integration work per element, not one shared change.
