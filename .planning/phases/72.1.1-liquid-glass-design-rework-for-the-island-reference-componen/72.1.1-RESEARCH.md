## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Effect Coverage
- **D-01:** The glass effect is **not confined to a rim** anymore. It follows the existing top-black → bottom-transparent gradient direction (`gradientMaterial`, unchanged direction from Phase 25/35 D-02) across the **whole island surface**, made glossier/more glass-like throughout — not just at the edge. This supersedes Phase 35 D-20a's rim-only scope for this phase's purposes (D-20a's rim mechanism may still inform *how* it's built, but the visible result is no longer rim-limited).
- **D-02:** Readability of text/icons **takes priority** over maximum glass intensity if the two conflict — same precedence Phase 35 already established (D-15: center darkness precedent) and consistent with every prior material decision in this project. If more glass coverage risks legibility, dial back the glass rather than the readability.

#### Visibility Across States (supersedes deferred transition bug)
- **D-03:** The glass look must be **consistently present in every island state** — collapsed pill, mid collapse↔expand animation, the small/compact expanded state, and the full expanded state. Not just the settled/idle look.
- **D-04:** This explicitly **resolves the known deferred bug** documented in `.planning/debug/resolved/liquid-glass-black-during-transition.md` (glass drops to flat black during collapse↔expand morph and tab switches) — that bug is now in-scope for this phase, not still deferred. The `GlassEffectContainer`/`.glassEffectID` approach mentioned as "attempted and reverted" in that doc is a known-bad prior attempt (caused the whole island to frost permanently) — do not repeat it as-is; research a different mechanism for continuous glass rendering during identity/geometry changes.
- **D-05:** No live mouse/pointer-driven reactivity (unlike the real macOS Dock's cursor-follow behavior). "Dynamic" in this phase means *state-driven* (glass present through every animation/state transition), not *pointer-driven*. Explicitly ruled out — do not build cursor-tracking distortion.

#### Scope: Island Shell + Selected Inner Elements
- **D-06:** The glass look extends beyond the outer island shell to specific elements **inside** the island:
  - Buttons/icons: Quick Action buttons, view-switcher tabs
  - Cards/tiles: Calendar event cards, the Weather widget, Tray file tiles
  - OSD bars/sliders: the Volume and Brightness bars (`OSDLevelBar`, just redesigned in Phase 72.1)
- **D-07 (interaction with Phase 72.1):** OSD bar glass treatment must **layer on top of, not replace**, Phase 72.1's locked opacity-ramp mechanic (D-01/D-02/D-03 in `72.1-CONTEXT.md`: fill brightness/opacity scales with fraction filled, colors stay fixed green/orange, no accent tint). The glass look is an additional visual layer on the bar, not a redesign of the fill-opacity behavior that phase just shipped. **RESEARCH NOTE: this mechanic was reverted same-day — see this document's Pitfall 4 / Open Question 1.**
- **D-08:** No other inner elements (e.g., Settings window content, onboarding) are in scope unless research finds they share a code path with one of the D-06 elements. Settings' existing calmer glass variant (Phase 35 D-08/D-09) is not explicitly touched by this discussion — flag to the user during planning if it turns out to need matching changes.

## Summary

This phase reworks an **already-working** native Liquid Glass implementation (Phase 35, shipped 2026-07-16) from a thin decorative rim (`LiquidGlassRimRingShape`, confined by user request in round 5's D-20a follow-up) back out to full-surface coverage, while simultaneously fixing a known, previously-deferred transition-flicker bug (D-04) and extending glass treatment to 6 separate inner-element render locations (D-06). None of this requires new third-party code, a new Swift package, or porting an actual React component — the reference component (`21st.dev/r/suraj-xd/liquid-glass`) is confirmed (both in the prior discuss-phase session and again in this research session) to be **unreachable for direct source inspection** (21st.dev blocks plain HTTP/WebFetch with 403; no Playwright/headless-browser tool is available in this environment, and curl with a realistic User-Agent also received 403). This is not a blocker: the reference is explicitly a *visual/behavioral* pointer only, and the technique class it points at (SVG/CSS displacement-map refraction + specular/rim highlight + backdrop blur) is **already fully documented and already ported into this codebase** as `reference-GlassSurface.md` / `LiquidGlassShader.metal` from Phase 35 — there is nothing new to port.

The real engineering work is architectural, not technique-discovery: (1) scale the existing native-glass call from a ring `Shape` back to the full island `Shape` (this exact code path was **live and working** before D-20a scoped it down for aesthetic, not technical, reasons — reverting is a proven, low-risk starting point, not new ground), while independently retuning the `<macOS 26` legacy shader fallback's rim-mask constants to match, since the deployment target is still 15.0 and the fallback path must satisfy D-01/D-03 too; (2) fix the transition-flicker bug via a **narrowly-scoped** `GlassEffectContainer` + shared `glassEffectID`, inside `liquidGlassEffectLayer` only — not wrapping the whole `presentationSwitch` (that exact wider-scope approach already caused a worse regression once and is explicitly ruled out by CONTEXT.md); (3) apply per-element `.glassEffect()`/material treatment at 6 genuinely separate call sites for D-06, none of which currently route through `islandFill`/`liquidGlassEffectLayer`.

One critical finding surfaced during this research that the planner **must** be told explicitly: **D-07's premise is stale.** The Phase 72.1 OSD-bar opacity-ramp mechanic (D-01/D-02/D-03 in `72.1-CONTEXT.md`) that D-07 says glass must "layer on top of, not replace" was **reverted** during Phase 72.1's own on-device UAT (quick task `260731-61m`, same day as this phase's CONTEXT was gathered) after the user disliked the dimming-toward-invisible effect on real hardware. `OSDLevelBar` (`NotchPillView.swift:5048-5061`) currently renders its filled `Capsule` at a plain, always-full opacity — there is no opacity ramp left to layer on top of. See Open Questions.

**Primary recommendation:** Do NOT attempt to fetch/port the 21st.dev component further — treat it as directional confirmation only. Build full-surface coverage by reverting `liquidGlassEffectLayer`'s native branch from `LiquidGlassRimRingShape` back to the full base `shape` (the pre-D-20a code path), retune the legacy shader's `edgeOpacity`/`centerOpacity`/`borderWidth` for the same full-coverage look on the `<macOS 26` fallback, fix D-04 via a `GlassEffectContainer` scoped strictly inside `liquidGlassEffectLayer` with a shared `glassEffectID` across all 4 call sites, and treat each of the 6 D-06 inner elements as its own small, independent `.glassEffect()` addition — grouped by control-vs-content risk profile, not by file proximity.

### Pattern 1: Full-surface native glass (D-01) — revert to pre-D-20a shape argument
**What:** Pass the full base `shape` (not `LiquidGlassRimRingShape`) to `.glassEffect(_:in:)`.
**When to use:** The native (macOS 26.0+) branch of `liquidGlassEffectLayer`.
**Example (this is literally what shipped between D-20 and D-20a — proven to compile and render):**
```swift
// Source: this codebase, NotchPillView.swift, Phase 35 round 5 (D-20, before D-20a's rim scope-down)
Color.clear
    .frame(width: size.width, height: size.height)
    .glassEffect(.regular.tint(Color.black.opacity(0.7)), in: shape)   // full `shape`, not LiquidGlassRimRingShape
    .allowsHitTesting(false)
```
Note the tint alpha (0.7) was the D-20 starting value before D-20a; re-tuning is expected (D-02 readability priority) and must go through the DEBUG tuner pattern, not a guessed literal.

### Pattern 2: Scoped GlassEffectContainer for transition continuity (D-04)
**What:** Wrap only the `.glassEffect(...)` call inside `liquidGlassEffectLayer` in a `GlassEffectContainer`, and give it a **stable, shared** `glassEffectID` (same string, same `Namespace`) at all 4 call sites, instead of the previously-reverted whole-`presentationSwitch` wrap.
**When to use:** Native (macOS 26.0+) branch only; this is the mechanism Apple's own glass-transition API exists for ("views conditionally shown/hidden trigger morphing with animation" — [CITED: conorluddy/LiquidGlassReference, cross-verified against createwithswift.com/serialcoder.dev]).
**Example:**
```swift
// Illustrative — not yet in this codebase. A dedicated @Namespace (separate from `ns`,
// the existing matchedGeometryEffect namespace) avoids cross-interference between the
// island's shape-morph tracking and the glass-morph tracking.
@Namespace private var glassNS

@ViewBuilder
private func liquidGlassEffectLayer(shape: NotchShape, size: CGSize, parameters: LiquidGlassParameters) -> some View {
    if materialStyle == .liquidGlass {
        if #available(macOS 26.0, *) {
            GlassEffectContainer {
                Color.clear
                    .frame(width: size.width, height: size.height)
                    .glassEffect(.regular.tint(Color.black.opacity(0.7)), in: shape)
                    .glassEffectID("islandGlass", in: glassNS)   // SAME id/namespace at all 4 call sites
                    .allowsHitTesting(false)
            }
        } else {
            legacyLiquidGlassEffectLayer(shape: shape, size: size, parameters: parameters)
        }
    } else {
        EmptyView()
    }
}
```
This is a genuinely different scope than the already-reverted attempt (which wrapped the entire `presentationSwitch`, not just this one function's output) and directly follows the debug file's own "Eliminated" guidance: *"if retried, scope the container much narrower (e.g. only inside liquidGlassEffectLayer itself) and iterate on-device incrementally, not in one blind jump."*

### Pattern 3: Legacy shader full-coverage retune (< macOS 26 fallback, required for D-01/D-03 regardless of native mechanism)
**What:** Widen `LiquidGlassParameters.collapsed`/`.expanded`'s `borderWidth`/`blurWidth` (the rim-band width) and reduce the `edgeOpacity`/`centerOpacity` contrast so the frost layer's dark center no longer dominates — the deployment target is 15.0, so this fallback path is still user-facing and must independently satisfy D-01 (not just mirror the native path's visual intent).
**When to use:** `legacyLiquidGlassEffectLayer`, called from the `else` branch.
**Note:** This reuses 100% of the existing shader functions (`liquidGlassEdgeOpacity`, `liquidGlassDistortion`) — pure parameter tuning, not new shader code, following the exact "Claude's Discretion" numeric-tuning convention already established in `35-CONTEXT.md`.

### Anti-Patterns to Avoid
- **Wrapping the whole `presentationSwitch` in a `GlassEffectContainer`:** Empirically caused the entire island to read as permanently frosted glass instead of the intended rim/full-surface look. Explicitly ruled out by CONTEXT.md D-04 and confirmed by this research as still the wrong scope.
- **Adding a new sibling/wrapper view for any of this work:** Every mechanism above plugs into the EXISTING `.overlay(liquidGlassEffectLayer(...))` call already present at all 4 shell call sites (`NotchPillView.swift:1378`, `2937`, `3219`, `3401`) — this project already broke `matchedGeometryEffect` continuity once (WR-02) by introducing a new sibling view for materials work; do not repeat that class of change.
- **Treating D-06 inner elements as one shared refactor:** They are 6 genuinely separate render locations with no shared code path today (confirmed by direct code read — see Runtime/Code Insights below). Planning them as "one glass modifier applied everywhere" risks under-scoping the on-device verification burden per element.
- **Pointer/cursor-tracking distortion:** Explicitly ruled out by D-05 — "dynamic" in this phase means state-driven only, never live mouse-follow, unlike the actual macOS Dock or the 21st.dev reference's own cursor-reactive behavior.

## Common Pitfalls

### Pitfall 1: Native glass over a large, continuously-animated shape is expensive and may worsen (not fix) the flicker
**What goes wrong:** `.glassEffect()` is backed by `CABackdropLayer`, documented (via this project's own prior debug session, `.planning/debug/resolved/liquid-glass-black-during-transition.md`) as compositing 3 offscreen textures — expensive per-frame. Scaling the glass region from a thin rim to the FULL island surface multiplies the compositing cost during every spring-animated transition, right as D-04 is trying to make that same transition flicker-free.
**Why it happens:** Apple's own WWDC25 design guidance states Liquid Glass is intended for the **navigation layer** (small chrome elements: toolbars, buttons) floating above content, explicitly *not* for large content-bearing surfaces [CITED: conorluddy/LiquidGlassReference, cross-referenced against createwithswift.com]. D-01 asks for exactly the discouraged usage pattern (a large, full-surface glass region).
**How to avoid:** Fix D-04 (transition continuity) FIRST against today's already-working rim-only shape, confirm on-device that the narrow-scoped `GlassEffectContainer` fix holds under animation, THEN scale to full-surface coverage as a separate, later on-device-checkpointed step. This isolates variables — if full-surface coverage reintroduces flicker, the planner will know it's the surface-area change, not the container-scoping mechanism, that's responsible.
**Warning signs:** Any regression back to flat-black/flat-color during collapse↔expand or tab-switch transitions after the full-surface change lands, even if the rim-only D-04 fix tested clean in isolation.

### Pitfall 2: Fixing only the native (macOS 26+) path leaves the shipped `<macOS 26` fallback out of compliance with D-01/D-03
**What goes wrong:** Deployment target is 15.0 (confirmed: `MACOSX_DEPLOYMENT_TARGET = 15.0` in `Islet.xcodeproj/project.pbxproj`). Any user on macOS 15-25 still gets `legacyLiquidGlassEffectLayer`'s rim-only look (D-12–D-18's narrow-band constants) even after the native path is scaled to full coverage — this silently fails D-01/D-03 for a real subset of users, not a theoretical one.
**Why it happens:** It's easy to treat "the build machine runs macOS 26" (true, confirmed) as license to only touch the native branch, since that's what's actually visible during development/UAT.
**How to avoid:** Explicitly include a legacy-shader retuning task (Pattern 3 above) in the plan, verified via `#if false` / temporarily forcing the `else` branch on-device (or via a Mac running an older macOS if available), not skipped as "unreachable in practice."
**Warning signs:** Plan only mentions `#available(macOS 26.0, *)` branch changes with no corresponding `legacyLiquidGlassEffectLayer`/`LiquidGlassParameters` task.

### Pitfall 3: D-06 content-surface elements (Calendar cards, Tray tiles, Weather widget) are a readability risk Apple's own guidance already anticipated
**What goes wrong:** Applying the same glass intensity used for shell/controls to text-and-data-dense content surfaces (Calendar event rows, file tiles, the Weather card) risks exactly the D-02 conflict CONTEXT.md already flags — glass intensity vs. legibility.
**Why it happens:** Apple's Liquid Glass design guidance itself singles out navigation-layer chrome (buttons, toolbars — i.e., Quick Action buttons and switcher tabs, both clean fits) as the intended use, and explicitly warns against glassifying content (lists/tables/media — i.e., Calendar cards, Tray tiles, Weather widget, all content surfaces).
**How to avoid:** Treat Quick Action buttons + switcher tabs as one risk tier (controls, safe for fuller glass intensity) and Calendar cards + Tray tiles + Weather widget as a second, lower-intensity risk tier — mirroring the exact precedent Phase 35 already established for the Settings window (D-08/D-09: "calmer half of the technique... without the distortion shader" for text/form-heavy surfaces).
**Warning signs:** On-device UAT reports text/icons becoming hard to read on any of the 3 content-surface elements — this is the expected failure mode to watch for specifically on those three, not the shell or the two control elements.

### Pitfall 4: D-07's stated interaction with Phase 72.1 no longer matches the shipped code
**What goes wrong:** `72.1.1-CONTEXT.md` D-07 instructs the OSD bar glass treatment to "layer on top of, not replace" Phase 72.1's opacity-ramp mechanic (D-01/D-02/D-03 of `72.1-CONTEXT.md`). That mechanic was **reverted** during Phase 72.1's own on-device UAT (`STATE.md` quick task `260731-61m`, 2026-07-31, commits `3729334`/`6a24409`) — the user disliked the dimming-toward-invisible effect on real hardware. `OSDLevelBar` (`NotchPillView.swift:5048-5061`) currently fills its `Capsule` at a plain, constant opacity; there is no ramp left to layer on top of, and no related `@AppStorage` keys remain in `ActivitySettings.swift` (confirmed by direct read — the file's own comment at line 119-122 documents the revert).
**Why it happens:** `72.1.1-CONTEXT.md`'s canonical_refs point to `72.1-CONTEXT.md`'s decisions as still-locked, but a same-day quick task superseded them after that context was written into the roadmap seed, and the discuss-phase session for 72.1.1 did not cross-check the live code state.
**How to avoid:** Flag this to the user before/during planning — D-07 should be read as "the OSD bar glass treatment applies to `OSDLevelBar`'s current always-full-opacity fill; there is no separate opacity mechanic to coordinate with" rather than as a real layering constraint. This is a simplification (one less thing to coordinate), not a blocker, but the planner should not silently plan against a mechanic that isn't there.
**Warning signs:** A plan or task description that references "the opacity ramp" for OSD bars as if it's live code — grep `ActivitySettings.swift`/`NotchPillView.swift` for `debugOSDOpacity` or similar before trusting any such reference; none exist as of this research.
