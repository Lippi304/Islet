## Fixed Issues

### CR-01: New D-06 glass call sites ignore the user's Material Style setting

**Files modified:** `Islet/Notch/NotchPillView.swift`, `Islet/Notch/ShelfItemView.swift`
**Commit:** `2cd0b7e`
**Applied fix:** All 6 call sites now gate on `materialStyle == .liquidGlass` before entering the
`#available(macOS 26.0, *)` branch, using the review's suggested compound-condition form
(`if materialStyle == .liquidGlass, #available(macOS 26.0, *) { ... } else { ... }`) rather than
nesting two `if` statements — behaviorally identical, one fewer indent level, and matches how the
codebase already writes compound availability guards elsewhere.

- `weatherFullContent` and `quickActionButton` — both already had `self.materialStyle` available
  (declared once at `NotchPillView`'s top, `:366`); only the gate itself was added.
- `navCircleButton` — same, `self.materialStyle` already in scope. Note this call site's fallback
  fill (`filled ? Color.white : Color.clear`) is unconditional in both the glass and non-glass
  branches — it is the base circle's own selected/unselected state, not the thing being gated —
  only the `.glassEffect()` overlay itself is now conditional on the new gate, exactly matching
  its pre-fix behavior on macOS < 26.
- `EventRow` and `OSDLevelBar` — both `private struct`s with no prior access to `NotchPillView`'s
  `@Environment` property. Each gained its own
  `@Environment(\.islandMaterialStyle) private var materialStyle` declaration, mirroring the
  identical pattern already on `NotchPillView` itself.
- `ShelfItemView` (`Islet/Notch/ShelfItemView.swift`) — separate file, zero prior `materialStyle`
  references. Same environment-property addition as above, reading through the pre-existing
  `\.islandMaterialStyle` environment key (`ActivitySettings.swift`) that
  `NotchWindowController.swift:3172` already injects at the window root, so no new plumbing was
  needed — just consuming the value that was already flowing down.

In all 6 cases the non-liquidGlass fallback is the exact pre-existing plain fill (`Color.white.opacity(...)` / `Circle().fill(...)` / `Capsule().fill(tint)`) — unchanged, matching what each element rendered before this phase added glass.

## Skipped Issues

### WR-01: Near-identical guarded-glass boilerplate duplicated 6 times with no shared helper

**File:** `Islet/Notch/NotchPillView.swift:2077-2089, 2654-2669, 2930-2944, 4897-4910, 5217-5223`; `Islet/Notch/ShelfItemView.swift:26-39`
**Reason:** skipped — 5 of the 6 call sites (`weatherFullContent`, `quickActionButton`, `EventRow`,
`OSDLevelBar`, `ShelfItemView`) do fit the review's suggested
`liquidGlassBackground(_:style:tint:materialStyle:)` helper cleanly: each is a single
`shape.fill(Color.clear).glassEffect(style.tint(tint), in: shape)` vs. `shape.fill(tint)` swap,
varying only in concrete `Shape`, `Glass` style, and tint expression — exactly what the helper
parameterizes.

`navCircleButton` does not. Its composition is structurally different: the base `Circle().fill(filled ? Color.white : Color.clear)` is the SAME concrete fill in both the glass and non-glass
branches (it encodes the button's selected/unselected state, not a materialStyle-dependent
choice), and the glass branch adds `.glassEffect(...)` as an extra overlay on top of that same
base rather than replacing a `Color.clear` placeholder with it. Forcing this site through the
generic helper (which assumes the glass branch's base fill is always `Color.clear`, standing in for the
solid `tint` fill used in the non-glass branch) would either lose the `filled` selected-state fill
under glass conditions, or require a second parameter/branch that defeats the point of a shared
helper. This is the "meaningful per-call-site variation that makes a shared helper awkward" case —
a partial refactor (5 of 6 sites through a helper, 1 left as hand-written) was judged higher risk
(inconsistent pattern, more surface for a future edit to miss) than no refactor, for a
non-blocking DRY finding. CR-01's fix was applied identically and correctly at all 6 sites
regardless (see above) — WR-01 is purely a duplication/maintainability concern, not a functional
gap.

**Original issue:** The `if #available(macOS 26.0, *) { <Shape>().fill(Color.clear).glassEffect(<style>.tint(<tint>), in: <Shape>()) } else { <Shape>().fill(<tint>) }` pattern is repeated near-verbatim 6 times across 2 files.
