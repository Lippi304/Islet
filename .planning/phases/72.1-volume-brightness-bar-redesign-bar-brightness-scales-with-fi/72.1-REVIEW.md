## Warnings

### WR-01: DigitRollText digit identity is left-anchored, so digit-count-boundary crossings roll the wrong character — **FIXED** (`2b57127`)

**Resolution:** Implemented via place-value tagging rather than the suggested `.reversed()` +
`.environment(\.layoutDirection, .rightToLeft)` approach — each digit is tagged with
`placeValue = digits.count - 1 - offset` and `ForEach` is keyed on `\.placeValue` directly,
while display order still follows the original left-to-right array (no layout-direction
flip needed). Verified: build succeeds, `ActivitySettingsTests` 23/23 pass. Not yet
re-verified on-device by the user for the specific 9↔10 / 99↔100 boundary crossings.


**File:** `Islet/Notch/NotchPillView.swift:5094-5106`
**Issue:**
```swift
ForEach(Array(String(displayValue).enumerated()), id: \.offset) { _, digit in
    ZStack {
        Text(String(digit))
            .id(digit)
            .transition(.move(edge: .top))
    }
    .frame(width: 8)
    .clipped()
    .transition(.move(edge: .top))
}
```
`id: \.offset` numbers digits from the **left** (index 0 = leftmost character). When
`displayValue` crosses a digit-count boundary this misaligns place value with position identity:

- `9 -> 10`: `String("9")` has one char at offset 0. `String("10")` has `"1"` at offset 0 and
  `"0"` at offset 1. ForEach reuses the view at offset 0 (same identity), so the inner
  `Text(digit).id(digit)` transitions from `"9"` straight to `"1"` — the digit that used to be
  the **ones** place visually rolls into the **tens** digit — while a brand-new `"0"` is
  inserted at offset 1. The ones-place digit ("9" rolling to "0") never actually happens; the
  tens digit ("1") appears to grow out of the old ones digit instead.
- Symmetrically, `10 -> 9` rolls `"1" -> "9"` at offset 0 and removes offset 1 (the actual `"0"`
  ones digit), i.e. the surviving digit slot shows the wrong transition and the digit that
  should persist (ones place) is the one that gets deleted.

The comment directly above this code (lines 5063-5071) explicitly calls out digit-count
boundary crossings ("9<->10, 99<->100") as requiring correct handling via two move-edge
transition sites — but only the *fade-vs-move* problem (D-04a) was solved; the *which digit
rolls* problem was not, because identity is anchored to the wrong end of the string. The final
displayed text is still correct ("10"/"9"), but the roll direction/target digit during the
crossing is semantically backward, which is exactly the visually "off" behavior the whole
DigitRollText rework exists to avoid.

**Fix:** Anchor identity to place value (from the right) instead of string offset, e.g.:
```swift
let digits = Array(String(displayValue))
ForEach(Array(digits.reversed().enumerated()), id: \.offset) { _, digit in
    ZStack {
        Text(String(digit)).id(digit).transition(.move(edge: .top))
    }
    .frame(width: 8)
    .clipped()
    .transition(.move(edge: .top))
}
.environment(\.layoutDirection, .rightToLeft) // or build the HStack right-to-left and re-reverse for display
```
(or equivalently, reverse the string, enumerate, then reverse the resulting array of views back
into left-to-right render order) so a digit-count change always inserts/removes at the
**leading** (left) slot and the ones-place digit's identity — and its 9→0 roll — stays anchored
to the rightmost slot across the boundary.

### WR-02: Debug OSD Roll Speed nudge has no lower-bound clamp

**File:** `Islet/Notch/NotchPillView.swift:3914`, `Islet/AppDelegate.swift:637-638`
**Issue:** `DigitRollText(value: percent, rollResponse: 0.30 + osdRollSpeedNudge)` feeds directly
into `.spring(response: rollResponse, ...)` (line 5116). `debugOSDRollSpeedNudge` is adjusted via
`adjustWingNudge(_:by:)` with no clamping in either direction — repeatedly clicking "Roll Speed
-0.05" in the DEBUG menu (`AppDelegate.swift:638`) can drive `rollResponse` to zero or negative,
an invalid value for SwiftUI's spring `response` parameter. This is the same "unbounded DEBUG
live-nudge" shape that already caused a real on-device freeze once in this codebase (commit
`c732446`, "clamp corner-radius nudge to prevent self-intersecting NotchShape"), which is why
that nudge is now clamped at the `NotchShape` level. `osdRollSpeedNudge` has no equivalent floor.
Release builds are unaffected (`osdRollSpeedNudge` always returns 0 there), so this is DEBUG-only
risk, not a Release regression — but it's a foot-gun for whoever runs the on-device tuning
workflow this menu exists for.

**Fix:**
```swift
private var osdRollSpeedNudge: Double {
    #if DEBUG
    return max(debugOSDRollSpeedNudge, -0.25) // keep 0.30 + nudge comfortably above 0
    #else
    return 0
    #endif
}
```

### WR-03: No test coverage for DigitRollText's rapid-repeat coalescing logic

**File:** `Islet/Notch/NotchPillView.swift:5083, 5109-5120`
**Issue:** The rapid-repeat gap-closure fix (`rapidRepeatThreshold`, `isRapid` computation in
`onChange(of: value)`) is new non-trivial branching logic — introduced specifically to fix a
real on-device bug (digits stuck mid-transition) — but ships with zero unit test coverage. This
breaks the codebase's own established discipline for exactly this class of view: `EqualizerBars`
exposes `targetHeight(bar:bucket:)` as `internal` specifically so `EqualizerBarsTests.swift` can
assert its range/determinism contract, and `OSDActivityTests.swift` covers the adjacent OSD
percent-clamping logic. `DigitRollText`'s coalescing decision has no equivalent seam or test, so
a future change (e.g. retuning `rapidRepeatThreshold` again) has nothing to regression-test
against, and the specific on-device bug this commit fixed has no safety net proving it stays
fixed.
**Fix:** Extract the decision into an internal, pure, testable function, mirroring
`EqualizerBars.targetHeight`'s precedent:
```swift
static func shouldCoalesce(now: Date, lastChangeTime: Date, threshold: TimeInterval = rapidRepeatThreshold) -> Bool {
    now.timeIntervalSince(lastChangeTime) < threshold
}
```
and add a small `DigitRollTextTests.swift` asserting `shouldCoalesce` at/around the 0.12s
boundary.
