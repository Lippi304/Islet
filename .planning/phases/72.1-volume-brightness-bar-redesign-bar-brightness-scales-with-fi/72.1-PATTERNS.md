### `OSDLevelBar` opacity ramp (D-01/D-02/D-03)

**File:** `Islet/Notch/NotchPillView.swift`, struct at lines 5040-5053
**Analog:** the struct's own existing track `Capsule` (same file, line 5047) — already uses `.opacity(0.15)` as a static constant; this phase makes the fill's opacity a `fraction`-driven ramp instead of the current implicit 1.0.

**Current code (lines 5040-5053) — this is what gets modified in place:**
```swift
private struct OSDLevelBar: View {
    let fraction: CGFloat
    let tint: Color

    var body: some View {
        GeometryReader { geo in
            ZStack(alignment: .leading) {
                Capsule().fill(Color.white.opacity(0.15))                       // empty track
                Capsule().fill(tint).frame(width: geo.size.width * fraction)    // filled (D-02 fixed tint)
                    .animation(.spring(response: 0.15, dampingFraction: 0.86), value: fraction)   // D-16 retuned value
            }
        }
    }
}
```

**Core pattern to add — opacity chained onto the SAME `Capsule` that already animates `.frame(width:)` via `value: fraction`:**
```swift
Capsule().fill(tint)
    .frame(width: geo.size.width * fraction)
    .opacity(opacityMin + (opacityMax - opacityMin) * Double(fraction))   // NEW: D-01 ramp, no floor per D-02
    .animation(.spring(response: 0.15, dampingFraction: 0.86), value: fraction)   // UNCHANGED — one spring drives both width + opacity
```
Because `.opacity` and `.frame(width:)` sit on the same view instance and read the same `fraction`, no second `.animation()` modifier is needed — this is a load-bearing detail from RESEARCH.md, confirmed by reading the existing single-`.animation()` structure directly.

**D-05 tuner read points to add to `OSDLevelBar`:** follow the exact `wingLeadingNudge`/`wingCornerRadiusNudge` always-compiled-computed-property shape at `NotchPillView.swift` lines 192-226 (excerpted below under Shared Patterns) — `opacityMin`/`opacityMax` become `0.0 + osdOpacityMinNudge` / `1.0 + osdOpacityMaxNudge` where the nudge properties are `#if DEBUG @AppStorage / #else 0` read points declared on the parent view (`NotchPillView`), then passed into `OSDLevelBar` as init params (mirrors how `fraction`/`tint` are already passed in — no `@AppStorage` inside `OSDLevelBar` itself, since it's a plain leaf struct, not the parent `View` that owns the other `@AppStorage` properties).

### `DigitRollText` new component (D-04/D-04a/D-04b)

**File:** `Islet/Notch/NotchPillView.swift`, replaces lines 3898-3907 inside `osdWings(for:)`, new struct placed near `OSDLevelBar` (~after line 5053)

**Current code being replaced (lines 3898-3907):**
```swift
Text("\(percent)")
    .font(.system(size: 11, weight: .semibold, design: .monospaced))
    .foregroundStyle(.white)                         // D-02: never accent-tinted
    .frame(width: percentTextWidth, alignment: .leading)
    // Quick task 260729-5pv: smooth roll+fade between old/new digits as percent
    // changes, mirroring OSDLevelBar's own local `.animation(value:)` convention
    // (D-16 spring constants) rather than relying on the outer wing's presence
    // transaction, which only animates appear/disappear, not in-place value changes.
    .contentTransition(.numericText(value: Double(percent)))
    .animation(.spring(response: 0.15, dampingFraction: 0.86), value: percent)
```

**Call-site replacement pattern** — same slot, same `percentTextWidth`/`percentGap` layout budget (lines 3847-3848, unchanged), only the Text's internals swap for a `DigitRollText(value: percent)` call:
```swift
DigitRollText(value: percent)
    .frame(width: percentTextWidth, alignment: .leading)
```

**New component skeleton (per-digit `.id()` + `.move` transition, never `.opacity`/`.push`)** — same animation constants (`response: 0.15, dampingFraction: 0.86`) as `OSDLevelBar`'s own spring, matching the existing project-wide "reuse the retuned D-16 spring" convention rather than inventing a new curve:

**Critical:** `.transition(.move(edge: .top))` must appear on BOTH the inner `Text` (fires on in-place digit character swaps, e.g. 4→5) AND the outer per-digit wrapper after `.clipped()` (fires when `ForEach(..., id: \.offset)` inserts/removes an entire digit position on a digit-COUNT change, e.g. 9→10, 100→99). The outer wrapper transition is not optional — omitting it makes digit-count boundary crossings fall back to SwiftUI's default opacity fade, violating D-04a.
```swift
private struct DigitRollText: View {
    let value: Int   // 0...100, already clamped upstream by OSDActivity.swift

    var body: some View {
        let digits = String(value).map { $0 }
        HStack(spacing: 0) {
            ForEach(Array(digits.enumerated()), id: \.offset) { _, digit in
                ZStack {
                    Text(String(digit))
                        .id(digit)                          // identity change triggers the in-place transition
                        .transition(.move(edge: .top))       // NOT .push(from:) — that fades, violates D-04a
                }
                .clipped()
                .transition(.move(edge: .top))               // REQUIRED: covers insert/remove of this whole
                                                              // digit position on digit-count changes (9→10,
                                                              // 100→99) — without this, ForEach's default
                                                              // insertion/removal fades, violating D-04a.
            }
        }
        .font(.system(size: 11, weight: .semibold, design: .monospaced))   // matches replaced Text exactly
        .foregroundStyle(.white)                                          // D-02 (Phase 39, locked): never accent-tinted
        .animation(.spring(response: 0.15, dampingFraction: 0.86), value: value)
    }
}
```
**Anti-pattern to avoid explicitly:** `.transition(.move(edge: .top).combined(with: .opacity))` reintroduces the exact fade the user rejected (D-04a) — keep `.move` alone. Also avoid `AnyTransition.push(from:)` — Apple's own docs confirm it fades on both insert and remove. Also avoid putting `.transition(.move(edge:))` ONLY on the inner `Text` — digit-count boundary crossings (9↔10, 99↔100) need the outer wrapper's own transition too.

**Pitfall to carry into planning:** `percentTextWidth: CGFloat = 22` (line 3848) was sized for the old plain Text; verify `value = 100` (3 digits) still fits — this is a real reachable value (`OSDActivity.swift`'s clamp allows exactly 100), not a hypothetical edge case.
