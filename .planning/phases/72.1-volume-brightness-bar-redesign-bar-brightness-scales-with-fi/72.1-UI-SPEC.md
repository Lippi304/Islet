# Phase 72.1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Platform note:** Islet is a native macOS SwiftUI app. Not React/Next.js/Vite — the shadcn initialization gate does not apply, and there is no component-registry layer to detect (confirmed: no `components.json`/`tailwind.config.*` anywhere in the repo). Design system is native SwiftUI (`OSDLevelBar`, SF Symbols, San Francisco system font) plus this codebase's own established OSD-wing conventions, extracted from `Islet/Notch/NotchPillView.swift`'s `osdWings(for:)` and this phase's own `72.1-CONTEXT.md`/`72.1-RESEARCH.md`.

**Scope note:** Two purely additive visual changes to ONE existing view function (`osdWings(for:)`) and ONE existing subview (`OSDLevelBar`). No new wing, no new layout region, no new Settings card, no new permission surface, no color/hue change. The user's shadcn `number-ticker` reference (https://21st.dev/r/dillionverma/number-ticker) is a **behavioral reference only** — reimplemented natively as `DigitRollText`, never installed as an actual package.

## Bar Opacity-Ramp Contract (D-01/D-02/D-03)

**Structural constraint:** modifies the existing `OSDLevelBar` struct's fill `Capsule` only — no new view, no restructuring of the track/fill two-layer composition.

| Property | Value |
|----------|-------|
| Mechanism | `.opacity(Double(fraction))` (or an eased variant, at planner/executor discretion per RESEARCH.md Pattern 1) applied to the same fill `Capsule` that already animates `.frame(width:)` — same `value: fraction` spring drives both simultaneously, no second `.animation()` modifier |
| Opacity at 0% fill | `0.0` — **no floor** (D-02, locked). Bar is allowed to become nearly invisible near empty. Do not clamp to a visible minimum "so the user can still see something is there" — that directly contradicts the locked decision. |
| Opacity at 100% fill | `1.0` — full, unchanged from today's constant-opacity look |
| Curve | Linear by default (`opacityMin + (opacityMax - opacityMin) * Double(fraction)`); eased is Claude's discretion per CONTEXT.md — pick whichever reads best on-device, no separate approval needed |
| Applies to | Both Volume (green) and Brightness (orange) bars, **identically** — same mechanic, same near-invisible-at-low-values behavior, no per-activity branching (D-03) |
| Hue/color | **Unchanged.** `Color.green` (volume) / `Color.orange` (brightness), fixed, never accent-tinted — this phase touches alpha only, never hue or the D-02 (Phase 39) fixed-color rule |
| Track (empty background) | Unchanged — `Color.white.opacity(0.15)`, does not participate in the ramp |
| Tunable via D-05 | `opacityMinNudge` / `opacityMaxNudge` — DEBUG-only, offset-additive on top of the baked `0.0`/`1.0`, following the Wing Tuner pattern. Starting values: `0.0` min, `1.0` max (literal, no epsilon) — RESEARCH.md Open Question 2 defers any epsilon decision to on-device tuning, not to this spec. |

## Percent Counter — Digit-Roll Contract (D-04/D-04a/D-04b)

**Structural constraint:** replaces the existing percent `Text`'s `.contentTransition(.numericText(value:))` (line ~3906) with a new small private view, `DigitRollText`. Position/sizing slot (`percentTextWidth: 22`, `percentGap: 10`) is unchanged — only the Text's content/transition mechanism changes.

**This is net-new component work (D-04b), not a spring/parameter retune.** `.contentTransition(.numericText(value:))` is rejected outright, confirmed unreadable during rapid key-repeat via the user's own on-device test.

| Property | Value |
|----------|-------|
| Mechanism | Per-digit `Text(String(digit)).id(digit)` inside a clipped `ZStack`, one sub-view per digit position, `.transition(.move(edge: .top))` — **never** `.combined(with: .opacity)`, never `AnyTransition.push(from:)` (both fade by design, disqualified by D-04a) |
| Digit opacity | Always fully opaque, at every point mid-transition — digits only translate (slide), never blend/fade/cross-dissolve |
| Font | `.system(size: 11, weight: .semibold, design: .monospaced)` — identical to today's percent `Text`, unchanged |
| Color | `.white`, fixed — D-02 (Phase 39, locked): never accent-tinted |
| Animation | `.spring(response: 0.15, dampingFraction: 0.86)` starting point — same spring already tuned for the bar's rapid-update behavior (39-07/39-08 gap-closure); retune via D-05's Roll Speed tuner if it reads too slow/fast against real key-repeat rate |
| Roll direction | Single fixed `.move(edge: .top)` for both increasing and decreasing values, shipped first (simplest reading of D-04a). Direction-aware (`.asymmetric(insertion:removal:)` keyed off previous value) is an explicit fallback only if the fixed version visibly reads wrong on-device (RESEARCH.md Open Question 1) — do not build direction-awareness preemptively. |
| Multi-digit boundary crossings (e.g. 39→40) | Both digit positions roll simultaneously — this is correct, expected odometer behavior (matches a real mechanical odometer), not a bug to guard against |
| 100% edge case | `value = 100` is a real, reachable 3-digit value — verify on-device that 3 digit sub-views still fit inside the existing 22pt `percentTextWidth` slot without clipping or overlap (RESEARCH.md Pitfall 3/Assumption A2). If it doesn't fit, widen `percentTextWidth`/`percentGap` minimally rather than shrinking per-digit width below legibility. |
| Tunable via D-05 | `osdRollSpeedNudge` — DEBUG-only, offset-additive on the spring's `response`, Wing Tuner pattern |

**Do not build:** a full odometer "reset" state machine (rotation3D digit wheels, staggered per-digit settle timing, synthetic intermediate steps) — that solves arbitrary-large-jump problems this phase's actual 0–100 range with small per-keypress deltas doesn't have. See RESEARCH.md "Don't Hand-Roll."

## DEBUG Tuner Contract (D-05)

Mirrors the existing Wing Tuner 3-file pattern exactly (`ActivitySettings.swift` keys → `NotchPillView.swift` `@AppStorage` read points → `AppDelegate.swift` `NSMenu` ± actions), same pattern used for SHAPE-03 (Phase 71) and every prior wing constant.

| Tuner axis | Key | Step | Starting baked value |
|------------|-----|------|----------------------|
| Opacity Min | `debug.wingTuner.osdOpacityMinNudge` | ±0.05 | 0.0 |
| Opacity Max | `debug.wingTuner.osdOpacityMaxNudge` | ±0.05 | 1.0 |
| Roll Speed | `debug.wingTuner.osdRollSpeedNudge` | ±0.05 | spring `response: 0.15` |

Menu location: new "OSD Bar/Counter Tuner" submenu inside the existing DEBUG menu, alongside the existing Wing Tuner submenu (`AppDelegate.swift` ~line 522). Reuses the existing `adjustWingNudge(_:by:)` helper — no new helper needed. Reuses existing `debugPreviewOSDVolume`/`debugPreviewOSDBrightness` "Preview Wing" menu items to trigger the OSD on demand during tuning, without needing to physically hold a volume/brightness key.

Release builds: all three nudges compile to `0`/unused via `#if DEBUG`/`#else` — zero behavior change outside DEBUG, matching every prior tuner axis.

This phase adds **zero new layout regions** — no new wing, no new width/padding constant beyond the existing OSD wing geometry. Only two existing render points inside the same fixed layout slot change: the fill `Capsule`'s opacity, and the percent `Text`'s transition mechanism.

| Region | Value | Source |
|--------|-------|--------|
| Bar width | 90pt (unchanged) | Existing constant, `barWidth` |
| Bar height | 5pt (unchanged) | Existing constant |
| Percent text width | 22pt (unchanged unless 100% edge case forces a minimal widen — see above) | Existing constant, `percentTextWidth` |
| Percent gap (bar → counter) | 10pt (unchanged) | Existing constant, `percentGap` |
| Per-digit sub-view width | Claude's discretion, monospaced-digit-width-driven (~7-8pt estimated, RESEARCH.md Assumption A2) — must fit 3 digits inside the 22pt slot at `value = 100` | New value, on-device visual check required |

Exceptions: per-digit sub-view width is new and unmeasured (flagged above) — this project's established convention (Phases 18/20/21/23/25/26/32/33/51/52, and now 71) is propose → live-tune on hardware → bake in with a comment, which D-05's tuner exists to support.

## Verification Notes for Executor

- **`OSDLevelBar` opacity change is a one-line addition** to the existing fill `Capsule` — do not restructure the two-layer track/fill composition, do not add a new `.animation()` modifier (the existing `value: fraction` spring already covers both width and opacity since both live on the same view instance).
- **`DigitRollText` is new, small, private** — placed near `OSDLevelBar` in `NotchPillView.swift`, same visibility level. Do not generalize it into a shared numeric-ticker component used elsewhere in the codebase; this phase's scope is the OSD percent counter only.
- **`.id(digit)` is load-bearing, not decorative** (RESEARCH.md Pitfall 5) — without it, SwiftUI diffs the `Text` in-place and `.transition()` never fires; the digit will snap instantly instead of rolling.
- **Never combine `.move` with `.opacity` in the transition, and never use `AnyTransition.push(from:)`** — both fade by design, which is exactly the rejected D-04 behavior. This is the single most important constraint in this spec; a reviewer/checker should treat any fade-adjacent transition modifier on the digit views as a spec violation, not a style preference.
- **No hue/hue-adjacent change anywhere in this phase** — `Color.green`/`Color.orange` stay byte-for-byte the same `Color` values; only `.opacity(...)` is added. If a reviewer sees a `Color(hue:saturation:brightness:)` interpolation or any HSB manipulation, that's out of scope (D-01 explicitly rejected it).
- **Verify `value = 100` on-device** specifically — 3-digit width in a slot sized for the old 2-character-typical `Text` is the one real layout-fit risk in this phase (RESEARCH.md Pitfall 3/Assumption A2).
- **Exact opacity min/max and roll timing are intentionally left as starting values above, not final** — D-05's DEBUG tuner exists specifically to confirm/adjust these on real hardware before baking in with a `// Quick task ... baked in from on-device tuning` comment, per this project's established convention. Do not treat the starting values in this spec as requiring a UI-SPEC amendment if they're tuned during execution — that's the intended workflow, not a deviation.
