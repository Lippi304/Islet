### Brightness Scaling (bar fill)
- **D-01:** The filled `Capsule`'s color brightness is driven by an **opacity ramp** — low fill = low opacity (dim), 100% fill = full opacity. Not a hue/lightness interpolation, not a glow effect — those were considered and rejected in favor of the simplest mechanism.

- **D-03:** Applies **identically** to both the Volume bar (green) and Brightness bar (orange) — same opacity-ramp mechanic, same near-invisible-at-low-values behavior, no per-activity difference.

- **D-04:** The existing `.contentTransition(.numericText(value:))` fade-based transition (added in Quick task 260729-5pv) is **rejected and replaced**. User tested the live debug build during this discussion and found the fade doesn't give enough time to read the current number when volume/brightness keys are pressed rapidly — digits blend into each other mid-fade.

## Summary

This phase is two additive, purely visual changes to one existing view function (`osdWings(for:)`) and one existing subview (`OSDLevelBar`) in `Islet/Notch/NotchPillView.swift`. Neither change touches `OSDActivity.swift`'s pure mapping layer, which stays untouched and fully covered by its existing tests.

**Change 1 (D-01/D-02/D-03 — opacity ramp):** `OSDLevelBar`'s filled `Capsule` currently renders at full, constant opacity regardless of `fraction`. The fix is a one-line addition: `.opacity(Double(fraction))` (or an eased variant) on the same `Capsule` that already animates `.frame(width:)` via `.animation(.spring(...), value: fraction)` — because opacity and width are both animatable properties on the *same* view driven by the *same* `value: fraction` trigger, no second `.animation()` modifier is needed; SwiftUI applies the one spring to both simultaneously. No hue/color change, no glow, no new component.

**Change 2 (D-04 — odometer counter):** The existing `.contentTransition(.numericText(value:))` on the percent `Text` (line 3906) is confirmed via research to be Apple's built-in "roll" transition, not the plain fade it replaced — but the user's own on-device test already established (during `/gsd-discuss-phase`) that it visibly blends/fades during rapid successive changes, which is the concrete, already-observed failure mode this phase must fix. This is genuinely net-new component work (D-04b): a small, self-built per-digit "digit roller" view, using `.id(digit)` + `.transition(.move(edge:))` (NOT `.push(from:)` — that transition fades by design, disqualifying it under D-04a) inside a clipped `ZStack`, one sub-view per digit position. This guarantees digits are always fully opaque and only ever translate, never blend — satisfying D-04a exactly. Full digit-by-digit "reset" animation logic (the kind built for arbitrary large jumps in blog-post odometers) is unnecessary complexity for this phase's actual 0–100, ±1-to-a-few-percent-per-keypress range — flagged explicitly under **Don't Hand-Roll** below so planning doesn't overbuild it.

**Primary recommendation:** Add `.opacity(Double(fraction))` to `OSDLevelBar`'s fill `Capsule` (same `value: fraction` spring already present), and replace the percent `Text`'s `.contentTransition(.numericText(value:))` line with a small custom `DigitRollText` view built from per-digit `Text.id(digit).transition(.move(edge:))` stacks — both changes wired through a new D-05 DEBUG tuner axis in `ActivitySettings.swift` + `AppDelegate.swift`, mirroring the existing Wing Tuner / SHAPE-03 3-file pattern exactly.

### Pattern 1: Opacity-ramp fill (D-01/D-02/D-03)
**What:** Fill `Capsule`'s alpha channel tracks `fraction` directly — no floor, no ceiling beyond 0...1.
**When to use:** Any bar-fill visual that should read as "dim when empty, bright when full."
**Example:**
```swift
// Source: adapted from existing OSDLevelBar (NotchPillView.swift:5040-5053) —
// only the .opacity(...) line and the two DEBUG-tunable constants are new.
private struct OSDLevelBar: View {
    let fraction: CGFloat
    let tint: Color

    // D-05 tuner axis — offset-additive, mirrors wingCornerRadiusNudge's own pattern
    // (Islet/Notch/NotchPillView.swift ~line 220). Baked constants (0.0 / 1.0) plus a
    // live DEBUG nudge, always-0 in Release.
    var opacityMinNudge: Double = 0   // read from a DEBUG @AppStorage-backed property, per D-05
    var opacityMaxNudge: Double = 0

    private var opacityMin: Double { 0.0 + opacityMinNudge }   // D-02: no floor by default
    private var opacityMax: Double { 1.0 + opacityMaxNudge }

    var body: some View {
        GeometryReader { geo in
            ZStack(alignment: .leading) {
                Capsule().fill(Color.white.opacity(0.15))                       // empty track — UNCHANGED
                Capsule().fill(tint)
                    .frame(width: geo.size.width * fraction)
                    .opacity(opacityMin + (opacityMax - opacityMin) * Double(fraction))   // NEW: D-01 ramp
                    .animation(.spring(response: 0.15, dampingFraction: 0.86), value: fraction)   // UNCHANGED — same trigger animates both width AND opacity
            }
        }
    }
}
```
**Note:** Because `.opacity(...)` and `.frame(width:)` are both applied to the *same* `Capsule` view instance and both read from `fraction`, the single existing `.animation(_:value: fraction)` modifier animates both simultaneously with the same spring — no restructuring of the animation wiring needed.

### Pattern 2: Digit-roll counter (D-04)
**What:** A `Text` is replaced with N per-digit sub-views, each independently transitioning via `.id()` + `.move(edge:)` when its own digit changes.
**When to use:** Any small (2-3 digit) counter needing "always legible, never fades" rolling behavior.
**Example (illustrative starting point — planner/executor tunes exact structure and animation timing per D-05):**
```swift
// Source: original synthesis — pattern verified against AnyTransition.move(edge:) semantics
// [CITED: Apple Developer Documentation, AnyTransition] and cross-checked against the
// "each digit view ... only the active digit is shown at rest" description of custom
// SwiftUI odometers [CITED: timm.preetz.xyz/p/swiftui-odometer].
private struct DigitRollText: View {
    let value: Int          // 0...100, already clamped upstream (OSDActivity.swift)
    let rollDuration: Double // D-05 tunable, e.g. via a DEBUG @AppStorage-backed nudge

    var body: some View {
        let digits = String(value).map { $0 }   // e.g. "42" -> ["4","2"], "100" -> ["1","0","0"]
        HStack(spacing: 0) {
            ForEach(Array(digits.enumerated()), id: \.offset) { _, digit in
                ZStack {
                    Text(String(digit))
                        .id(digit)   // changing this identity is what triggers the transition
                        .transition(.move(edge: .top))   // NOT .push(from:) — that fades (see Alternatives Considered)
                }
                .frame(width: 8)          // fixed per-digit width, monospaced font recommended
                .clipped()                // hides the outgoing/incoming digit outside the frame
            }
        }
        .font(.system(size: 11, weight: .semibold, design: .monospaced))   // matches existing Text (line 3899)
        .foregroundStyle(.white)                                          // D-02 (Phase 39, locked): never accent-tinted
        .animation(.spring(response: 0.15, dampingFraction: 0.86), value: value)
    }
}
```
**Open implementation question for planning (see Open Questions):** whether roll direction (up when increasing / down when decreasing) needs an explicit `.asymmetric(insertion:removal:)` transition keyed off a tracked "previous value," or whether a single fixed `.move(edge: .top)` reads acceptably in both directions on-device. Left to on-device tuning per D-05/Claude's Discretion ("exact odometer roll animation timing/easing/duration").

### Anti-Patterns to Avoid
- **`AnyTransition.push(from:)`:** Looks like the perfect one-line native replacement, but fades by design — directly violates D-04a. Confirmed via Apple's own documentation description, not just inference.
- **Combining `.move` with `.opacity` in the transition:** e.g. `.transition(.move(edge: .top).combined(with: .opacity))` — reintroduces exactly the blend the user rejected. Keep the transition to `.move` alone.
- **Full odometer "reset" state machine for arbitrary jumps:** the blog-post-grade odometer pattern (rotation3D digit wheels, staggered per-digit settle timing, synthetic intermediate steps capped at 20) solves a different problem (arbitrary large jumps, e.g. playlist counts). This phase's real domain is 0-100 with typical per-keypress deltas of 1-16 — a direct per-digit `.id()`+`.move` transition covers it without that machinery.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| "Digit changed, animate it" | A hand-written interpolation/step-counter that manually increments through every intermediate integer to "simulate" a roll | SwiftUI's built-in `.id()`-triggered `.transition()` + `.animation(value:)` | SwiftUI already re-triggers the transition automatically whenever the `.id()` changes — no manual timer/step loop needed for this phase's magnitude of change |
| "Brightness scales with value" | A custom `Color` blend (e.g. `Color(hue:saturation:brightness:)` interpolation) | Plain `.opacity(fraction)` on the existing fixed `tint` | D-01 explicitly rejected hue/lightness interpolation in favor of the simplest mechanism (alpha only) — building a color-space interpolator would be solving a problem D-01 already ruled out |
| "New tunable constant needs live UI" | A bespoke settings panel / slider UI for the new opacity min/max and roll timing values | The existing Wing Tuner `@AppStorage` + `NSMenu` ± buttons 3-file pattern (D-05) | This exact problem (constants that need on-device tuning before baking in) has a proven, working, already-built solution used for 6+ prior constants in this same codebase (leading/trailing/margin/gap/corner-radius nudges) |

**Key insight:** Every piece of this phase has a same-file, already-proven precedent (`OSDLevelBar`'s own opacity on the track, the Wing Tuner pattern, SwiftUI's own transition system) — there is no part of D-01 through D-05 that requires inventing a new mechanism from scratch.

## Common Pitfalls

### Pitfall 1: `.numericText()` "should" roll but observably fades under rapid changes
**What goes wrong:** Research confirms `.contentTransition(.numericText(value:))` is documented and generally understood to produce a digit-roll effect, not a fade [CITED: multiple SwiftUI tutorials cross-verified]. Yet the user's own on-device test (documented in `72.1-CONTEXT.md`, D-04) showed it blending/fading during rapid key-repeat. Community reports independently corroborate that `numericText` "in normal SwiftUI Views" (as opposed to Live Activities/widgets) can degrade to a fade or blink under certain conditions [source: community reports found via WebSearch, LOW confidence on exact root cause — see Assumptions Log A1].
**Why it happens:** Most likely candidates (unverified — Apple does not document exact interruption semantics for `numericText`): (a) the transition's internal digit-alignment logic falls back to a plain crossfade when it cannot cleanly correlate old/new glyph runs, which can happen more often under rapid re-triggering; (b) a new value arriving mid-animation restarts/interrupts the in-flight transition, and the interruption itself renders as a blend rather than a clean redirect.
**How to avoid:** Do not attempt to "fix" `.numericText()` by retuning its spring — this phase replaces it entirely with the custom `.move`-only transition in Pattern 2, which has no such fallback path (a `.move` transition has no glyph-correlation step to fall back from).
**Warning signs:** If the eventual custom digit-roll ever shows a flash of blended/overlapping digits during rapid key-repeat testing, check first for an accidentally-added `.opacity` in the transition chain (Anti-Patterns above) before assuming it's an interruption bug — that combination is the most common way to reintroduce exactly this symptom.

### Pitfall 2: Multi-digit boundary crossings roll more than one digit at once
**What goes wrong:** Going from 39% to 40% changes both the tens and ones digit simultaneously (39→40, both digits' identities change). A naive implementation might expect only the tens digit to visibly move.
**Why it happens:** Each digit position is independently keyed by its own character value — when both positions' characters change in the same update, both trigger their own `.transition()` in the same animation frame. This is expected, correct odometer behavior (matches how a real mechanical odometer's wheels behave), not a bug.
**How to avoid:** Do not add cross-digit synchronization logic to "prevent" this — it's the intended visual. Just confirm on-device that simultaneous multi-digit rolls still read cleanly (this is exactly the kind of judgment call D-05's live-tuning menu exists for).
**Warning signs:** If simultaneous digit rolls look chaotic on real hardware, the fix is timing/easing tuning (D-05), not restructuring which digits transition.

### Pitfall 3: `100%` is a 3-digit value in a layout sized for 2
**What goes wrong:** `percentTextWidth: CGFloat = 22` (line 3848) was sized for the old plain-fade `Text`. A 3-digit `100` rendered via 3 independently-widthed digit sub-views could overflow or misalign against this fixed-width slot.
**Why it happens:** The current code confirms `percent` is genuinely `0...100` inclusive (see `OSDActivity.swift`'s clamp: `min(100, max(0, percent))`), so `100` is a real, reachable value (full volume/brightness), not a hypothetical edge case.
**How to avoid:** Verify the `DigitRollText` layout at `value = 100` specifically during on-device testing — either give the container a flexible width that still fits inside `percentTextWidth`'s existing budget, or confirm 3 digits of the chosen `.frame(width:)` per digit still fit in 22pt (monospaced digits at `size: 11` are typically ~7-8pt wide each, so 3×7.5pt ≈ 22.5pt is borderline — this needs an on-device visual check, not just an assumption).
**Warning signs:** Clipped or overlapping "100" text specifically (other values render fine).

### Pitfall 4: Rapid successive `withAnimation` triggers from held-down volume/brightness keys
**What goes wrong:** Holding a volume/brightness key fires many rapid updates (system key-repeat rate, typically far faster than the ~0.15s spring's settle time). Each update re-triggers both the opacity/width spring on the bar and the digit-roll transition.
**Why it happens:** SwiftUI's `.animation(_:value:)` and `.transition()` are both designed to retarget cleanly mid-flight when the underlying value changes again before the current animation finishes — this is standard, well-supported SwiftUI behavior, not a special case this phase needs to build for.
**How to avoid:** No special code is needed for this — the same spring (`response: 0.15, dampingFraction: 0.86`) already handles rapid `fraction` updates for the bar's width today (this is exactly what 39-07/39-08's own gap-closure comments in the code, lines 5025-5039, were tuned for). Reuse it as the starting point for the digit-roll's `.animation(value:)` too, then confirm feel on real hardware per D-05.
**Warning signs:** If digits visibly "stutter-freeze" or skip values during rapid key-repeat, the animation duration is too slow relative to key-repeat rate — shorten `response` via the D-05 tuner.

### Pitfall 5: `Text.id(_:)` transitions require a real `ZStack`/container identity change to fire
**What goes wrong:** A common mistake is applying `.transition(...)` to a view without changing anything about its *identity* — SwiftUI transitions only fire on insertion/removal (identity changes), not on in-place property mutation. Simply changing `Text("\(digit)")`'s string content without an `.id()` change results in an in-place diff (SwiftUI just updates the string), and `.transition()` never fires at all.
**Why it happens:** This is the most common gotcha reported across every SwiftUI transitions tutorial found in this research — transitions are fundamentally an insert/remove mechanism, easy to reach for as if it were a property animator.
**How to avoid:** The `.id(digit)` in Pattern 2's example is load-bearing, not decorative — it is what forces SwiftUI to treat each new digit value as a new view identity, triggering insertion of the new digit and removal of the old one (which is what makes `.transition(.move(edge:))` apply at all).
**Warning signs:** If the digit just snaps instantly to the new value with zero animation, the `.id()` is missing or not actually changing.

## Open Questions

1. **Does the roll transition need direction-awareness (up when increasing, down when decreasing)?**
   - What we know: A single fixed `.move(edge: .top)` will always animate the same way regardless of whether the value went up or down.
   - What's unclear: Whether this reads acceptably on real hardware, or whether users will find a "wrong-direction" roll (e.g. rolling up while the value is actually decreasing) confusing — the shadcn `number-ticker` reference the user cited generally does direction-match.
   - Recommendation: Ship the simpler fixed-direction version first (per D-04b's "net-new but don't overbuild" framing and this project's own propose→tune→bake convention), confirm on-device via D-05's tuner + Preview Wing menu items, add direction-awareness only if the fixed version visibly reads wrong.

2. **Exact opacity floor value: literal 0.0, or a tiny epsilon (e.g. 0.02) to avoid a fully-invisible bar being mistaken for "nothing rendered"?**
   - What we know: D-02 explicitly locks "no minimum-opacity floor... nearly invisible is allowed, do not clamp to a visible minimum."
   - What's unclear: Whether "nearly invisible" in the user's own framing tolerates literal `opacity: 0` at `fraction: 0`, or whether a hairline epsilon reads better without contradicting D-02's intent.
   - Recommendation: Start at literal `0.0` (simplest, most literal reading of D-02) and let the D-05 "Opacity Min" tuner surface any need for an epsilon during on-device testing — this is exactly the kind of value D-05 exists to resolve.
