# Phase 72.1: Volume/Brightness Bar Redesign - Context

**Gathered:** 2026-07-31
**Status:** Ready for planning

<domain>
## Phase Boundary

The Volume/Brightness OSD wing (`osdWings(for:)` in `NotchPillView.swift`) gets two visual changes: (1) the fill bar (`OSDLevelBar`) becomes brighter/more opaque the fuller it is, and near-empty it becomes barely visible; (2) the percent counter next to it is replaced with a proper roll/slide odometer-style ticker that stays fully readable during rapid successive value changes (holding down a volume/brightness key). Both Volume and Brightness bars get identical treatment. Colors stay fixed (green/orange, never accent-tinted) per the existing locked D-02 decision from Phase 39 — this phase only touches opacity/alpha and the counter's transition mechanism, not hue.

</domain>

<decisions>
## Implementation Decisions

### Brightness Scaling (bar fill)
- **D-01:** The filled `Capsule`'s color brightness is driven by an **opacity ramp** — low fill = low opacity (dim), 100% fill = full opacity. Not a hue/lightness interpolation, not a glow effect — those were considered and rejected in favor of the simplest mechanism.
- **D-02:** No minimum-opacity floor. At very low values (~0-5%) the bar is allowed to become **nearly invisible** — matches the user's own framing ("kurz vor 0 kaum Helligkeit"). Do not clamp to a visible minimum.
- **D-03:** Applies **identically** to both the Volume bar (green) and Brightness bar (orange) — same opacity-ramp mechanic, same near-invisible-at-low-values behavior, no per-activity difference.

### Percent Counter (odometer ticker)
- **D-04:** The existing `.contentTransition(.numericText(value:))` fade-based transition (added in Quick task 260729-5pv) is **rejected and replaced**. User tested the live debug build during this discussion and found the fade doesn't give enough time to read the current number when volume/brightness keys are pressed rapidly — digits blend into each other mid-fade.
- **D-04a:** Replacement must be a **roll/slide (odometer) transition, never an opacity fade/blend** — digits stay fully opaque at all times and only move (slide up/down like a mechanical counter), so the number is always legible even mid-transition. This is the behavior the user's original shadcn `number-ticker` reference (https://21st.dev/r/dillionverma/number-ticker) was pointing at — build a native SwiftUI equivalent of that rolling-digit look, not a tuned version of the existing `.numericText()` transition.
- **D-04b:** This is net-new component work (a real digit-rolling ticker), not a parameter tweak — flagged explicitly so planning doesn't underscope it as "adjust spring values."

### DEBUG Tuner
- **D-05:** New values introduced by this phase (opacity ramp min/max, odometer roll speed/timing) get a **new DEBUG-only tuner axis**, following the exact existing Wing Tuner pattern: `#if DEBUG`-gated `@AppStorage` keys in `ActivitySettings.swift`, NSMenu +/- buttons in `AppDelegate.swift`. This mirrors Phase 71's SHAPE-03 precedent and the project-wide "propose a value → live-tune on hardware → bake in with a comment" convention — every other wing constant in this codebase was tuned this way.

### Claude's Discretion
- Exact opacity min/max numeric values (subject to on-device tuning via D-05).
- Exact odometer roll animation timing/easing/duration.
- Number and size of DEBUG tuner step increments, menu item labels/ordering (follow existing Wing Tuner menu convention).
- Whether the opacity ramp is linear or eased — pick whatever reads best on-device.

</decisions>

## Existing Code Insights

### Reusable Assets
- `OSDLevelBar` (`NotchPillView.swift:5040`) — already isolated as its own struct with a `fraction`/`tint` interface; the opacity ramp is an additive modifier on the fill, no restructuring needed
- Wing Tuner `@AppStorage`/NSMenu 3-file pattern — directly reusable template for the new D-05 tuner axis, same file locations as Phase 71's SHAPE-03 addition

### Established Patterns
- "Propose a value → live-tune on hardware via a DEBUG menu → bake in the on-device-confirmed number with a `// Quick task ... Round N: baked in from on-device tuning` comment" — applies to the new opacity min/max and odometer timing values
- The percent `Text` already occupies a fixed layout slot (`percentTextWidth`/`percentGap`) inside `osdWings(for:)` — the new odometer ticker replaces only the Text's content/transition logic, not its position/sizing

### Integration Points
- `osdWings(for:)` is the single, universal entry point for both the Volume and Brightness OSD wings — both D-01/D-02/D-03 (bar) and D-04 (counter) changes land in this one function plus `OSDLevelBar`
- No other OSD render path exists — `OSDActivity` is the only data source consumed by this view
