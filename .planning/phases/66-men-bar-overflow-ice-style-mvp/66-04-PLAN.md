<objective>
Wire `MenuBarOverflowController` into `AppDelegate`: own it as a stored property (mirroring
`quickNotesController`'s menu-bar-only ownership shape, never `NotchWindowController`'s
`ActivitySettings`-gated activity lifecycle — per D-02 this feature has no toggle), construct the
chevron `NSStatusItem` only once permission is confirmed (D-04), placed leftmost (D-01), and route
its click to `toggleReveal()` (D-05).

66-03 built is inert without this wiring. Isolating it to `AppDelegate.swift` alone (no
`NotchWindowController` involvement) keeps this feature in the same "menu-bar-only, zero resolver
participation" category as Quick Notes (Phase 64 D-13), per CONTEXT.md D-02's explicit citation.
Output: A real chevron users can see and click, gated correctly on Accessibility trust.

    constructMenuBarOverflowChevron()` that builds the chevron exactly like `statusItem`'s
    construction shape (interfaces above) using SF Symbol `chevron.left` (collapsed default,
    accessibility description "Show hidden menu bar items" per the UI-SPEC table above), assigns
    the result to `menuBarOverflowChevron`, and immediately writes its screen frame into
    `menuBarOverflowController.chevronFrame` (the button's `window?.frame`, read after the item is
    added to the status bar). In `applicationDidFinishLaunching`, BEFORE the existing `statusItem =
    NSStatusBar.system.statusItem(...)` line (line 107) — this ordering is D-01's "added to
    NSStatusBar.system before those two so it lands to their left" — set
    `menuBarOverflowController.onReady = { [weak self] in self?.constructMenuBarOverflowChevron()
    }` then call `menuBarOverflowController.start()`. If already trusted at launch, `onReady`
    fires synchronously inside `start()` and the chevron is constructed before line 107 runs; if
    untrusted, the chevron simply does not exist yet (D-04) and gets constructed later whenever
    the controller's health-check confirms a mid-session grant — document in a comment that in
    that later case AppKit's own status-item ordering behavior may not place it strictly leftmost
    relative to already-existing items (an accepted best-effort limitation, not a bug, since exact
    z-ordering-on-late-add is not guaranteed by AppKit).
  </action>
