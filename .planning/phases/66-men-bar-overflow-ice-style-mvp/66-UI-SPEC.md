# Phase 66 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Revision (2026-07-28, second pivot — D-07):** Supersedes the 2026-07-27 version below in full. That version was written entirely for the spacer-`NSStatusItem` mechanism (D-06), which NO-GO'd on-device in Plan 66-04 (spacer `.length` toggle has zero reclaim effect, Cmd-drag never engages). CONTEXT.md has since pivoted a second time: the phase now debugs the original private-CGS mechanism (Ice's own technique) against a real, currently-running Ice.app on this machine, rather than building a third mechanism. **This reopens MENUBAR-04** (the Accessibility permission prompt) — the old version below explicitly forbade any permission UI because it assumed the spacer technique (no permission required at all). That assumption no longer holds: Ice's own private-CGS mechanism requires Accessibility, and Islet's CGS spike (Plan 66-01) almost certainly does too.

**What carries over unchanged (confirmed working on-device in Plan 66-04's UAT):** the chevron control itself — icon-only `NSStatusItem`, SF Symbol glyph, `chevron.left`/`chevron.right` two-state toggle, leftmost placement, `autosaveName`, no attached `NSMenu`, inline (not popover) reveal. Only the *underlying hide/reveal mechanism* and the *permission surface* change in this revision.

**What is removed:** the entire "Spacer — invisible, non-interactive" contract and its two `Spacing Scale` length values (`btnHiddenLength` / screen-width-clamped expanded length) — those belonged exclusively to the now-abandoned spacer technique. The CGS mechanism hides/reveals real menu-bar item windows directly; there is no second, invisible, width-toggling status item in this revision.

**What is newly added:** a one-time Accessibility permission-explanation popover, a visible (non-silent) degraded state when permission is denied, and one new informational row in Settings — all specified below. This is the phase's first-ever Settings surface and first-ever popover; everything else remains menu-bar chrome only (no notch/pill UI, still zero).

## Permission Contract (MENUBAR-04 — reopened this revision)

This is the one genuinely new UI surface in this phase. It must be **visible, not silent** (CONTEXT.md's explicit requirement) — no version of "the chevron just quietly doesn't work" is acceptable.

### One-time explanation (first launch, not yet trusted)

- **Trigger:** at app launch, if `AXIsProcessTrusted()` is `false` **and** a one-time `UserDefaults` flag (e.g. `hasShownMenuBarOverflowPermissionExplanation`) is not yet set, show the permission popover exactly once, ever — it must never reappear on subsequent launches even if the user dismisses it via `"Not Now"` and permission remains denied. (The durable, every-launch signal for a still-denied state is the Settings row below, not a recurring popover.)
- **Anchor:** Islet's existing always-present main status item (the `capsule.fill` icon at `AppDelegate.swift:107`), via a plain AppKit `NSPopover` wrapping an `NSHostingController` of the SwiftUI view described below — **not** the chevron itself, since the chevron does not exist yet at this point (see Degraded State below: chevron is absent until permission is granted).
- **Content:** title `"Menu Bar Overflow"` (15px semibold), body copy (12px regular, 1.4 line height, exact text in Copywriting Contract above), two buttons (`"Not Now"` / `"Open System Settings"`) — pixel-identical layout to `osdPermissionExplanationView`/`capsLockPermissionExplanationView` (16px padding, 280px width, 8px vertical spacing).
- **`"Open System Settings"` action:** deep-links to `x-apple.systempreferences:com.apple.preference.security?Privacy_Accessibility` (the exact working prefix already proven in this codebase), then dismisses. Does **not** additionally fire `AXIsProcessTrustedWithOptions(prompt: true)` in the same moment — the deep link IS the path to grant; a duplicate native prompt on top of an explanation popover the user just read would be redundant, not clearer.
- **`"Not Now"` action:** dismisses, sets the one-time flag, takes no other action. The chevron remains absent (see below) until the user separately grants access and relaunches (or the app re-checks — exact re-check timing is an implementation/planning decision, not a visual contract concern).

### Degraded state (permission denied, every launch thereafter)

- **Chevron:** absent from the menu bar entirely — the chevron `NSStatusItem` is never constructed while `AXIsProcessTrusted()` is `false`. (Locked decision, carried forward from this phase's original discussion — "Chevron fehlt, Settings zeigt Hinweis" — never superseded, only reopened for whether a permission gate exists at all, not for what the gate's visible behavior should be once it does.) This is a **visible absence**, not a disabled/grayed-out chevron — there is nothing in the menu bar suggesting the feature exists until permission is granted.
- **Settings:** exactly one new row, appended below the existing 5-row `permissionsSection` list at `SettingsView.swift:566-582`, **visible only while `AXIsProcessTrusted()` is `false`** — rendered nowhere at all once trusted (deliberate, explicit divergence from D-11's "always-visible 5-row list" precedent, which applies only to the 5 `PermissionKind` cases; this row is not a 6th `PermissionKind` and must not be added to `grantedPermissionCount`/the "X of 5" rollup text, since Accessibility already has its own bespoke, rollup-external handling elsewhere in this codebase for OSD and Caps Lock). Row layout clones `permissionRow`'s exact visual shape (icon left, label+reason stacked, status pill right, whole-row tap target) but is a standalone view, not a `PermissionKind` case:

| Element | Value |
|---------|-------|
| Icon | SF Symbol `menubar.rectangle`, `.foregroundStyle(.secondary)` |
| Label | `"Menu Bar Overflow"`, 13px regular |
| Reason text | `"Hide other apps' menu bar icons behind a chevron"`, 12px regular, `.secondary` |
| Status pill | `"Accessibility Needed"`, `xmark.circle.fill`, `.red` — same visual weight as the existing denied-state pill |
| Tap action | Whole row deep-links to `x-apple.systempreferences:com.apple.preference.security?Privacy_Accessibility` (identical URL to the popover's button) — always deep-links, no `notYetAsked`→request-API branch, since Accessibility has no `requestAuthorization(completion:)`-style API (matches the existing OSD/Caps Lock precedent of deep-link-only, never a native re-request call). |

- **Re-grant flow:** granting access in System Settings and returning to Islet (relaunch, or an active poll/health-check — implementation detail, not a visual contract concern) causes the chevron to appear and the Settings row to disappear on the next check. No confirmation toast/animation is specified for this transition — it is a plain appear/disappear, matching this phase's existing "instant, no animation" convention (see Reveal/hide animation below).

## Menu Bar Icon Contract (phase-specific — read before implementing)

### Chevron — two-state icon (unchanged from prior revision, confirmed working on-device in Plan 66-04)

The chevron's glyph swaps with the hidden section's state, so its direction always signals what a click will do next:

| State | Glyph | `accessibilityDescription` | When |
|-------|-------|------------------------------|------|
| Hidden section **hidden** (icons off-strip) — **default on first launch** | `chevron.left` | `"Show Hidden Menu Bar Icons"` | No persisted UI state yet, or last-persisted state was hidden |
| Hidden section **revealed** (icons visible) | `chevron.right` | `"Hide Menu Bar Icons"` | User has clicked the chevron to reveal |

Both glyphs are template images (`isTemplate = true`), no `SymbolConfiguration` override. Rationale for defaulting to **hidden** on first launch unchanged: reduces menu-bar clutter, matches the feature's own purpose.

### Chevron placement & identity (unchanged)

- Leftmost among Islet's own menu-bar items (D-01), constructed **only when `AXIsProcessTrusted()` is `true`** (new this revision — see Permission Contract above; the prior revision's spacer mechanism needed no such gate).
- `autosaveName = "IsletMenuBarOverflowChevron"` — stable, hardcoded string, so macOS's own position table anchors this item consistently across relaunches. Do not change this string once shipped.
- No `NSMenu` attached, no click routing beyond the reveal/hide toggle handler — clicking the chevron never opens a dropdown/popover (D-05: reveal happens inline in the menu bar itself, via the CGS mechanism's own repositioning, not a spacer-width change).

### Reveal/hide animation (unchanged: Claude's Discretion, CONTEXT.md D-05)

**None — instant state change**, matching Ice's own actual behavior (which this phase now debugs directly against). Whatever mechanism ultimately drives the CGS-based hide/reveal, it is not animated — this is a deliberate simplification carried forward from the prior revision, not a new decision.

### Islet's own items — exempt by construction, not enforcement (unchanged)

Per CONTEXT.md's default discretion assumption: Islet's own existing `statusItem`/`debugStatusItem` are positioned to the right of the chevron at construction time (visible zone) but are **not** programmatically prevented from being Cmd-dragged behind it — no public API exists for that. No self-heal check is built for this MVP. Do not add copy or UI promising unhideable icons.
