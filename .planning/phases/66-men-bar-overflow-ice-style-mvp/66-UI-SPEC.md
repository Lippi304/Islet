# Phase 66 — UI Design Contract: Menübar-Overflow (Ice-Style MVP)

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope reminder:** This phase's UI surface is a native `NSStatusItem` chevron in the macOS menu bar plus a small Settings permission-status card. No notch/island SwiftUI view is touched by this phase (per 66-CONTEXT.md scope boundary) — the shadcn gate, web spacing/typography framing below are adapted to this project's native-AppKit/SwiftUI convention, not a web design system.

## Spacing Scale

Declared values (must be multiples of 4), for the Settings permission-status card only — the chevron `NSStatusItem` itself has no app-controlled spacing (OS-sized menu-bar chrome):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | `lineSpacing` fine-tuning on explanation body text (`12 * 0.4`, matches `osdPermissionExplanationView`) |
| sm | 8px | VStack row spacing inside the permission-status card (matches `permissionRow`'s `HStack(spacing: 8)`) |
| md | 16px | Popover/card internal padding when the card renders as a `.padding(16)` block (matches `osdPermissionExplanationView`/`capsLockPermissionExplanationView`) |
| lg | 20px | Outer `Form` padding for the Settings section hosting this card (matches every existing section: `permissionsSection`, `weatherSection`, `diagnosticsSection` — all `.padding(20)`) |

Exceptions: the chevron `NSStatusItem`'s own icon glyph size (~18×18pt, SF Symbol default rendering inside a ~22pt-tall menu-bar button) is OS-controlled via `NSStatusItem.variableLength`, not part of this app-level 8pt scale — mirrors `AppDelegate.swift:107-115`'s existing status-item construction exactly, no new sizing decision needed.

## Menu Bar Chevron Contract

(Extends the template — this phase's primary UI element is a native `NSStatusItem`, not a web component, so its states are specified here explicitly for the executor.)

| State | SF Symbol | Accessibility description | Notes |
|-------|-----------|---------------------------|-------|
| Hidden section collapsed (default) | `chevron.left` | "Show hidden menu bar items" | Template image (`isTemplate = true`), monochrome, auto-tinted light/dark — matches `AppDelegate.swift:112-114`'s existing icon construction pattern exactly |
| Hidden section revealed (post-click, D-05) | `chevron.right` | "Hide menu bar items" | Same construction, glyph flips to indicate the toggle direction (standard macOS disclosure-chevron convention) |
| Accessibility permission denied (D-04) | — (chevron `NSStatusItem` is never created) | — | No broken/dead icon ever appears — the item simply does not exist until permission is granted, per D-04 |

**Placement:** Leftmost among Islet's own status items (D-01) — constructed the same way as `statusItem`/`debugStatusItem` (`AppDelegate.swift:107`, `:490`), added to `NSStatusBar.system` before those two so it lands to their left.

**Reveal/hide animation (D-05, inline in the menu bar):** Target 0.2s ease-in-out reposition — deliberately faster/subtler than the notch's fluid Dynamic-Island spring (response 0.6 / damping 0.62 from Phase 25), since this is ordinary native menu-bar chrome, not the island. **This target is constrained by the SC#1 on-device spike's findings** (66-RESEARCH.md Pitfall 3: the underlying synthetic-`CGEvent`-drag mechanism may not support a smooth custom animation at all) — if a smooth animated slide is not achievable via the validated mechanism, an instant reposition (no animation) is an acceptable fallback; the spike determines which is achievable, this contract sets the target to aim for.

**Click target:** Standard `NSStatusItem.button` click handling (mirrors `statusItem.button?.action` pattern at `AppDelegate.swift:306`) — single click toggles reveal/hide state (D-05); no menu attached to the chevron item itself (distinct from the main `statusItem`'s `NSMenu`).

## Settings Permission-Status Card

(Extends the template — this is the D-04 "Permission required" surface.)

**Placement:** Its own small `Section` (mirrors `weatherSection`/`diagnosticsSection`'s `ScrollView(.vertical) { Form { Section(...) { ... } } }.padding(20)` shape), recommended in the **System** sidebar section (Phase 27's `NavigationSplitView` categories: General/Workspace/System/About) since this is a system-level menu-bar mechanism, not workspace/shelf content — not explicitly locked by CONTEXT.md, so treat as a default the planner may relocate if a better-fitting section exists.

**Distinct from the existing `permissionsSection` 5-item rollup:** Accessibility is deliberately **not** added as a 6th row to `permissionsSection` (`SettingsView.swift:566-594`) — that rollup's "X of 5 granted" copy and `PermissionKind` enum are exhaustively scoped to the 5 read/data permissions (Location/Calendar/Bluetooth/Focus/Input Monitoring) with a native request-or-deep-link flow. Accessibility-gated features in this codebase (OSD suppression, Caps Lock) instead each get their own toggle-tied one-time explanation popover — but Menübar-Overflow has **no toggle** (D-02), so neither existing pattern fits verbatim. Per 66-RESEARCH.md's own Architectural Responsibility Map ("a new permission-status card, distinct from a feature-toggle card"), this phase gets its own small, **persistent** (not popover-dismissible) status card that live-updates via the same `AXIsProcessTrusted()` health-check timer pattern as `CapsLockMonitor.start()`.

**Card content by state:**
- **Granted:** feature-name title (15px semibold) + green "Active" status glyph (`checkmark.circle.fill`, matches `statusView`'s `.granted` case) + the one-line confirmation copy above. No button.
- **Denied:** "Permission required" title (15px semibold, D-04 verbatim) + red status glyph (`xmark.circle.fill`, matches `statusView`'s `.denied` case) + the explanation body copy (12px, `lineSpacing(12 * 0.4)`) + "Open System Settings" button deep-linking to `x-apple.systempreferences:com.apple.preference.security?Privacy_Accessibility` (verbatim URL string, copy-pasted from `SettingsView.swift:760`/`:790`/`:655`).
