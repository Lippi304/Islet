# Phase 67.1: Notch Size Scaling — Resolution-Aware + Manual Override - Context

**Gathered:** 2026-07-26
**Status:** Ready for planning

<domain>
## Phase Boundary

The notch island's **expanded content** (Home, Tray, Weather, Calendar, Quick Actions, Switcher) is sized entirely from fixed pt constants (`expandedSize`, `traySize`, `calendarWidth`, `weatherMediumContentHeight`, etc. in `NotchPillView.swift`) that do not adapt when the user picks a different scaled screen resolution. This phase adds (1) an automatic scale factor derived from the display's current scaled resolution, and (2) two manual Settings sliders (width, depth) the user can nudge further — so the island stops looking "too small" after a resolution change, without needing a per-resolution redesign of every view.

<decisions>
## Implementation Decisions

### Skalierungs-Scope
- **D-01:** One global scale factor applies uniformly across ALL expanded views (Home, Tray, Weather, Calendar, Quick Actions, Switcher) — not per-view calibration. It multiplies through the existing fixed-pt constants consistently, preserving today's proportions between views.
- **D-02:** The collapsed/idle pill is explicitly OUT of scope. It stays coupled to the physical notch geometry (`notchSize()`/`notchFrame()` in `NotchGeometry.swift`), which already tracks scaled-resolution changes automatically since it's computed from live points, not a fixed constant. Only expanded content scales.

### Manuelle Kontrolle
- **D-03:** Two independent Settings sliders — **Width** and **Depth** — not a single proportional slider, not fixed presets. User explicitly chose independent per-axis control over a locked-proportion single slider (accepted tradeoff: can produce non-proportional layouts; no view is currently built for independent W/H scaling, so this is new ground for research/planning).
- **D-04:** Slider range: **80%–150%** for both axes.

### Automatischer Auslöser
- **D-05:** Auto-detection IS in scope for v1 (not manual-only). It's driven by the display's current **scaled resolution** (points), not physical screen size/diagonal.
- **D-06:** Reference baseline ("100%") = **1470×956 points** — the resolution at which today's fixed pt constants look correctly sized (user-supplied, empirically measured). User's current problem resolution is **1710×1112**, where the island now looks too small.
  - Verified ratio: 1710/1470 ≈ 1.1633, 1112/956 ≈ 1.1632 — width and height scale **uniformly** with the chosen resolution at these two data points, meaning a single auto-scale-factor formula (not independent width/height auto-factors) is sufficient: `scaleFactor ≈ currentScreenWidthPoints / 1470` (equivalently via height / 956).

### Zusammenspiel Auto + Manuell
- **D-07:** Auto computes a default scale factor for the currently detected resolution; the two manual sliders start at (and can move away from) that computed default.
- **D-08:** Only **one global manual value** exists — not remembered per-resolution. Switching resolutions recomputes the auto default; the manual offset is a flat adjustment applied regardless of which resolution triggered the recompute (no per-resolution memory in v1).

### Claude's Discretion
- Exact mechanism for detecting a "scaled resolution changed" event (e.g. `NSApplication.didChangeScreenParametersNotification` vs. the existing display-resolver's own change path).
- Exact `@AppStorage` key names/persistence for the two manual scale values, following `ActivitySettings`' established key-namespace pattern.
- Whether the Settings sliders display percentage or absolute-pt labels.
- Exact math for combining auto-default + manual-offset (additive vs. multiplicative) — resolve during planning/research; D-07's intent is "manual starts at the auto value and moves from there."
- Visual placement of the two new sliders within Settings (new card vs. existing section) — not discussed, resolve during UI-spec.

</decisions>
