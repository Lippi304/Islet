<domain>
## Phase Boundary

The notch island's **expanded content** (Home, Tray, Weather, Calendar, Quick Actions, Switcher) is sized entirely from fixed pt constants (`expandedSize`, `traySize`, `calendarWidth`, `weatherMediumContentHeight`, etc. in `NotchPillView.swift`) that do not adapt when the user picks a different scaled screen resolution. This phase adds (1) an automatic scale factor derived from the display's current scaled resolution, and (2) two manual Settings sliders (width, depth) the user can nudge further — so the island stops looking "too small" after a resolution change, without needing a per-resolution redesign of every view.

**Amendment (2026-07-26):** the phase boundary now also covers a **collapsed-pill live re-measurement bug** — the collapsed pill must always match the real physical camera notch, at any resolution, immediately after a live resolution switch (no relaunch required). This is a correctness fix to the existing live-measurement path, NOT new scaling scope (see D-09/D-10).

<decisions>
## Implementation Decisions

### Skalierungs-Scope
- **D-01:** One global scale factor applies uniformly across ALL expanded views (Home, Tray, Weather, Calendar, Quick Actions, Switcher) — not per-view calibration. It multiplies through the existing fixed-pt constants consistently, preserving today's proportions between views.
- **D-02:** The collapsed/idle pill is explicitly OUT of scope. It stays coupled to the physical notch geometry (`notchSize()`/`notchFrame()` in `NotchGeometry.swift`), which already tracks scaled-resolution changes automatically since it's computed from live points, not a fixed constant. Only expanded content scales.

### Manuelle Kontrolle
- **D-03:** Two independent Settings sliders — **Width** and **Depth** — not a single proportional slider, not fixed presets. User explicitly chose independent per-axis control over a locked-proportion single slider (accepted tradeoff: can produce non-proportional layouts; no view is currently built for independent W/H scaling, so this is new ground for research/planning).
- **D-04:** Slider range: **80%–150%** for both axes.

### Automatischer Auslöser
- **D-05:** Auto-detection IS in scope for v1 (not manual-only). It's driven by the display's current **scaled resolution** (points), not physical screen size/diagonal.
- **D-06:** Reference baseline ("100%") = **1470×956 points** — the resolution at which today's fixed pt constants look correctly sized (user-supplied, empirically measured). User's current problem resolution is **1710×1112**, where the island now looks too small.
  - Verified ratio: 1710/1470 ≈ 1.1633, 1112/956 ≈ 1.1632 — width and height scale **uniformly** with the chosen resolution at these two data points, meaning a single auto-scale-factor formula (not independent width/height auto-factors) is sufficient: `scaleFactor ≈ currentScreenWidthPoints / 1470` (equivalently via height / 956).

### Zusammenspiel Auto + Manuell
- **D-07:** Auto computes a default scale factor for the currently detected resolution; the two manual sliders start at (and can move away from) that computed default.
- **D-08:** Only **one global manual value** exists — not remembered per-resolution. Switching resolutions recomputes the auto default; the manual offset is a flat adjustment applied regardless of which resolution triggered the recompute (no per-resolution memory in v1).

### Amendment 2026-07-26: Collapsed Pill Live Re-Measurement Bug
On-device UAT (67.1 Plan 05) found the collapsed pill genuinely mismatched to the real camera notch after switching to a non-baseline scaled resolution (1710×1112) — user-confirmed as a real alignment defect, not a "looks small next to bigger expanded content" perception issue.

**Root-cause framing established during this discussion** (informs planning, not prescriptive): at a higher-point-count scaled resolution, the physical camera notch legitimately occupies *fewer points* — so the collapsed pill correctly shrinking in points is expected, matching-hardware behavior. D-02 was right that this needs no D-01 scale factor. The user confirmed the defect appears **immediately** after a live resolution switch (System Settings → Displays), with no app relaunch needed — pointing at a re-measurement/refresh bug rather than a wrong formula. Symptom reported: position stays fixed, but depth (height) ends up too small / no longer matching the camera right after the live switch.

- **D-09:** D-02 is REAFFIRMED, not reversed — the collapsed pill still must NEVER receive the D-01 global scale factor or the manual width/depth sliders (D-03/D-04). It must stay pixel-perfect to whatever the OS reports as the real camera notch, at all times.
- **D-10:** This phase now ALSO requires a correctness fix so the collapsed pill's live-measured size stays correctly synced to the real notch immediately after ANY live resolution change — no stale/cached value, no relaunch needed. Exact root cause (e.g. `NSScreen.auxiliaryTopArea` staleness after `didChangeScreenParametersNotification`, a timing/settle race, or something else) is Claude's discretion to diagnose during research/planning — user has confirmed only the observed symptom and its timing, not the mechanism.

**Resolution (Plan 06, confirmed on-device):** root cause was NOT NSScreen staleness — a live on-device D10-TRACE showed the notification handler and `positionAndShow` both report the NEW resolution's values on the very first firing, both switch directions. The actual bug was render-layer: `matchedGeometryEffect`-tracked frames (`collapsedIsland` and the shared `wingsShape` helper) could ride along on an ambient SwiftUI animation transaction from an unrelated simultaneous state change, letting the live-measured size visibly lag. Fixed with `.animation(nil, value: size)` on both. User confirmed on-device: the bare idle pill AND every `wingsShape`-backed glance (OSD/CapsLock/Charging/Focus/Device/Update/Download/Timer/Meeting) now re-sync instantly.

### Amendment 2026-07-26 (second): Collapsed-State Live Activity Content — Manual Slider Retarget

During Plan 06's re-verification, the user found the Music-Play wing (`mediaWingsRow`) still broken — it never uses `interaction.collapsedNotchSize` at all (unlike osdWings/capsLockWings), just a fixed `Self.wingsSize.width` (290pt) frame with a naive `Spacer()` for camera clearance. At the user's non-baseline resolution the real camera cutout exceeds that fixed reserve: album art and the 5th equalizer bar get clipped, and the wing's overall depth doesn't reach the real camera.

An auto-resolution-driven fix (mirroring osdWings' explicit camera-block pattern, content size unchanged) was implemented and demonstrated — but the user rejected the AUTOMATIC-per-resolution approach entirely and redirected: repurpose the phase's existing two manual sliders instead.

- **D-11:** The plain idle collapsed pill (no active Live Activity — `collapsedIsland`, D-02/D-09's original subject) remains hardware-pixel-fixed, unaffected by any slider. Reaffirmed, not reversed.
- **D-12:** The two existing Width/Depth sliders (previously D-03/D-04, targeting the EXPANDED state) are RETARGETED to control the size of collapsed-state Live Activity wing content instead (Music, OSD volume/brightness, Caps Lock, Charging, Focus/DND, Device, Update, Download, Timer, Meeting, Countdown) — "the Island grows wider/deeper from the inside" per the user's own framing. This is a full retarget, not an addition: the same two sliders, new target.
- **D-13:** The EXPANDED state (Home/Tray/Weather/Calendar/Quick Actions/Switcher/Timer-setup) keeps ONLY the existing automatic resolution-driven scale factor (D-05/D-06) going forward — no manual slider offset applies to it anymore. `currentWidthScale`/`currentDepthScale` in `NotchWindowController` (currently auto+manual combined) become auto-only for every expanded panel-frame site they drive.
- **D-14:** The collapsed-state wing content reuses the SAME auto+manual combination mechanism already built for D-07/D-08 (auto computes a resolution-driven default from `islandAutoScaleFactor`/`resolvedIslandScale`, the slider offsets from there) — retargeted from expanded constants to wing constants, not reinvented. Camera-safety floor is non-negotiable: whatever the slider position, wing content must never visually overlap/shrink into the real camera cutout — the auto-computed default (not the manual offset) is what must guarantee that floor, mirroring how `resolvedIslandScale`'s 0.8–1.5 clamp already bounds the existing sliders.

### Reusable Assets
- `NotchGeometry.swift`'s pure functions (`notchSize`, `notchFrame`, etc.) — pattern to follow for a new pure scale-factor function (e.g. `islandScaleFactor(screenWidth:) -> CGFloat`), testable without a live `NSScreen`.

### Established Patterns
- **"Geometry three-site rule"** (this project's own recurring precedent: `blobShape` / `positionAndShow` / `visibleContentZone` must stay consistent) — this phase's scale factor is a multiplier threaded through the same three call sites, not a fourth parallel path.
- Pure-function-first architecture for geometry (`NotchGeometry.swift`) — mirrors this phase's own auto-scale-factor calculation as a testable pure function, separate from the live `NSScreen` wiring.

### Integration Points
- `NotchPillView.swift`'s per-view size constants — each multiplied by the scale factor (width constants × widthScale, height/depth constants × depthScale).
- Settings — two new sliders (Width/Depth); exact placement is Claude's discretion (UI-spec stage).
- Screen-change detection — likely `NSApplication.didChangeScreenParametersNotification` (or the existing display-resolver's own notification path) triggers recomputing the auto default.

### Collapsed-pill re-measurement (D-09/D-10 amendment)
- The recompute path (`didChangeScreenParametersNotification` → `updateVisibility()` → `positionAndShow(on:)` → `interaction.collapsedNotchSize`) already exists and looks architecturally correct end-to-end — the bug (if confirmed) likely lives in a layer below this app's control (stale `NSScreen` values, a settle-timing race beyond the existing `DispatchQueue.main.async` hop, or a similar platform-level lag) rather than a missing recompute call. Research should verify with a live debug-log trace (log `target.safeAreaTop`/`auxLeftWidth`/`auxRightWidth` immediately in the notification handler vs. a few run-loop ticks later) before proposing a fix, rather than assuming which layer is stale.
