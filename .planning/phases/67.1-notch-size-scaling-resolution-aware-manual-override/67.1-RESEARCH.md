User explicitly chose independent per-axis control over a locked-proportion single slider (accepted tradeoff: can produce non-proportional layouts; no view is currently built for independent W/H scaling, so this is new ground for research/planning).
- **D-04:** Slider range: **80%–150%** for both axes.
- **D-05:** Auto-detection IS in scope for v1 (not manual-only). It's driven by the display's current **scaled resolution** (points), not physical screen size/diagonal.
- **D-06:** Reference baseline ("100%") = **1470×956 points** — the resolution at which today's fixed pt constants look correctly sized (user-supplied, empirically measured). User's current problem resolution is **1710×1112**, where the island now looks too small.
  - Verified ratio: 1710/1470 ≈ 1.1633, 1112/956 ≈ 1.1632 — width and height scale **uniformly** with the chosen resolution at these two data points, meaning a single auto-scale-factor formula (not independent width/height auto-factors) is sufficient: `scaleFactor ≈ currentScreenWidthPoints / 1470` (equivalently via height / 956).
- **D-07:** Auto computes a default scale factor for the currently detected resolution; the two manual sliders start at (and can move away from) that computed default.
- **D-08:** Only **one global manual value** exists — not remembered per-resolution. Switching resolutions recomputes the auto default; the manual offset is a flat adjustment applied regardless of which resolution triggered the recompute (no per-resolution memory in v1).

## Summary

This phase has **no external-library surface at all** — it is pure Swift/SwiftUI/AppKit math layered onto a codebase whose geometry architecture is already fully mapped out (`NotchGeometry.swift`, `NSScreen+Notch.swift`, `DisplayResolver.swift`) and already has a proven, repeatedly-used convention for exactly this kind of change: the project's own **"geometry three-site rule"**. Every fixed-pt content constant in `NotchPillView.swift` (e.g. `expandedSize`, `traySize`, `calendarWidth`, `weatherMediumContentHeight`, `quickActionsBarContentHeight`, `homeContentHeight`, `switcherContentHeight`, `calendarContentHeight`) is read from **three independent call sites** — `NotchPillView.body`/`blobShape` (Site 1, what actually renders), `NotchWindowController.positionAndShow()` (Site 2, the physical window frame reservation), and `NotchWindowController.visibleContentZone()` (Site 3, the click-through hit-test rect). All three MUST agree on the scaled value or the project's own well-documented "CR-01 click-swallowing/dead-zone" regression class reappears — this has already bitten the project at least 4 times (Phase 32, 33, 44, 48, 65 comments all reference it explicitly).

The good news: the existing settings-apply pipeline (`UserDefaults.didChangeNotification` → `handleSettingsChanged()` → `updateVisibility()` → `positionAndShow()`) already re-runs Site 2 on **every** UserDefaults write, and NotchPillView already has a precedent (`topEdgeCutoutWidth`) for reading live `NSScreen` data directly inside the SwiftUI view with no controller plumbing, refreshed for free whenever `interaction.collapsedNotchSize` republishes on a screen-parameter change. This means the "live update, no debounce" requirement from the UI-spec and the "auto-recompute on resolution change" requirement from D-05 both fall out of the *existing* architecture almost for free — IF the new scale-aware constants are computed properties (or plain-value reads), never re-introduced as `static let`.

The single biggest planning risk is **scope completeness**: D-01's phrasing ("ALL expanded views... Home, Tray, Weather, Calendar, Quick Actions, Switcher") enumerates 6 surfaces, but the codebase has at least 8 more expanded/HUD surfaces built on the *exact same* fixed-pt-constant pattern (Timer/Pomodoro setup, Meeting HUD wings, Output-panel, Onboarding, Caps Lock/Update/Download/Focus wings) that are NOT in that list. Left unscaled, these will look inconsistently sized next to the 6 that do scale. This needs an explicit planner/user decision, not a silent assumption either way.

**Primary recommendation:** Add one pure, unit-testable function (`islandAutoScaleFactor(screenWidthPoints:baseline:)` in a new file sibling to `NotchGeometry.swift`) plus two `@AppStorage` manual-offset keys read directly at all three existing sites (mirroring `weatherStyleKey`'s direct `UserDefaults.standard` read at Sites 2/3 and `@AppStorage` at Site 1) — do not build a new environment-injection/theme-re-host mechanism; the existing settings-apply pipeline already covers it.

### Pattern 1: Pure auto-scale-factor function (mirrors `NotchGeometry.swift`'s existing ISL-01 contract)

**What:** A pure function taking a plain `CGFloat` screen width in points and the locked 1470pt baseline (D-06), returning a multiplier — no live `NSScreen`, fully unit-testable exactly like `hasNotch`/`notchSize`.
**When to use:** Called from Site 1 (View, fed by a live screen-width read) and Sites 2/3 (Controller, fed by the already-resolved `target: ScreenDescriptor` / `currentBuiltin()`).
**Example:**
```swift
// Source: verified pattern — Islet/Notch/NotchGeometry.swift (read directly, ISL-01 doc comments)
// D-06: 1470pt baseline is the LOCKED reference width where today's constants read correctly.
func islandAutoScaleFactor(screenWidthPoints: CGFloat, baseline: CGFloat = 1470) -> CGFloat {
    guard baseline > 0 else { return 1.0 }
    return screenWidthPoints / baseline
}
```

### Pattern 2: Manual offset stored as a delta from the auto default (RECOMMENDED — resolves the D-07/D-08 "additive vs multiplicative" open item)

**What:** Persist a flat **additive offset** per axis (not the absolute slider value), so D-07 ("sliders start at the auto default") and D-08 ("flat adjustment applied regardless of which resolution triggered the recompute") are both satisfied by construction, with only 2 stored numbers.
**When to use:** Both manual-scale `@AppStorage` keys.
**Example:**
```swift
// PROPOSAL — not yet implemented; tags this as a research recommendation, not a verified fact.
// effective = clamp(auto(currentScreen) + storedOffset, 0.8, 1.5)   — D-04's slider range is the CLAMP, not the offset's own range.
// Slider binding computes the effective value for display/drag, and writes back OFFSET = newValue - currentAuto.
// "Reset to Auto" simply sets storedOffset = 0.
func resolvedIslandScale(auto: CGFloat, manualOffset: CGFloat, range: ClosedRange<CGFloat> = 0.8...1.5) -> CGFloat {
    (auto + manualOffset).clamped(to: range)
}
```
This keeps the UI-SPEC's `Slider(value: $widthScale, in: 0.8...1.5)` binding shape (a single 0.8–1.5 displayed value) while still technically storing a resolution-independent offset underneath — the Slider's `Binding` getter/setter does the auto+offset arithmetic, the raw `@AppStorage` only ever holds the offset.

### Pattern 3: Reuse the existing settings-apply pipeline instead of building a new re-host mechanism

**What:** `handleSettingsChanged()` (fired from the existing `UserDefaults.didChangeNotification` observer, `NotchWindowController.swift` MARK "Phase 6") already ends with `renderPresentation()` + `updateVisibility()` → `positionAndShow()` on every settings write, including unrelated keys (documented in the `AppliedTheme` comment: *"UserDefaults posts didChangeNotification for EVERY defaults write"*).
**When to use:** No new observer, no new "did the scale change" diffing struct needed — Site 2 already recomputes on every slider drag tick for free. Site 1 recomputes for free on re-render since `@AppStorage` triggers a SwiftUI body re-evaluation on its own key's change.
**Example:** No new code — this is a "don't build" pattern, not a "build" one. The planner should verify this behavior with a task, not construct new plumbing for it.

### Pattern 4: Site 1's live screen-width read has an exact precedent already shipped (`topEdgeCutoutWidth`)

**What:** `NotchPillView.swift:2771-2783` already independently resolves the live built-in notched screen with zero controller plumbing, for the Phase 52 top-edge switcher's cutout-width computation.
**Example:**
```swift
// Source: Islet/Notch/NotchPillView.swift:2777-2782 (read verbatim, existing shipped code)
private var topEdgeCutoutWidth: CGFloat {
    guard let target = selectTargetScreen(from: NSScreen.screens.map { $0.descriptor }) else { return 0 }
    return topEdgeCutoutGap(screenWidth: target.frame.width, ...)
}
// The SAME shape, reused for the auto scale factor:
private var autoIslandScale: CGFloat {
    guard let target = selectTargetScreen(from: NSScreen.screens.map { $0.descriptor }) else { return 1.0 }
    return islandAutoScaleFactor(screenWidthPoints: target.frame.width)
}
```
This confirms Site 1 needs **no new notification observer** either — it re-evaluates this computed property on every `body` re-render, and `body` already re-renders on every `interaction.collapsedNotchSize` change, which `positionAndShow()` (Site 2) already re-publishes on every `didChangeScreenParametersNotification` (per the existing observer at `NotchWindowController.swift:594-602`).

### Anti-Patterns to Avoid

- **Re-introducing `static let` for any scaled constant:** The moment `expandedSize`/`traySize`/etc. need to vary at runtime, they cannot remain compile-time `static let CGSize` — they need to become computed (`static func` taking a scale, or instance-level computed properties that read the live scale). Leaving them as `static let` while trying to "scale" them at call sites risks scaling only SOME call sites and not others — exactly how the CR-01 dead-zone class started in prior phases.
- **Scaling `cameraClearance` (42pt) naively at the depth axis's 80% floor:** See Pitfall 1 below — this constant exists specifically to clear the physical camera housing, which does not shrink when the user picks 80% depth.
- **Reading `backingScaleFactor` or physical pixel dimensions:** D-05/D-06 are explicit that the trigger is the scaled-resolution **points** value (`NSScreen.frame.width`), the same value `NotchGeometry.swift` already uses everywhere. Retina backing-scale (pixels-per-point) is a completely different, irrelevant number here — do not conflate the two.
- **A second `NSApplication.didChangeScreenParametersNotification` observer:** One already exists and already drives both Site 2 (directly) and Site 1 (transitively, via `interaction.collapsedNotchSize`). A second observer risks double-firing / race conditions the codebase's own Pitfall-6 comment already warns about ("this can fire several times / mid-transition").

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Detecting the built-in notched display | A new screen-selection heuristic | `selectTargetScreen(from:)` (`DisplayResolver.swift`, already used by both Sites 1/2/3 elsewhere) | Already handles the "which display" question correctly (`isBuiltin && hasNotch`, never by array index) — reusing it means multi-monitor/external-display attach-detach is a **non-issue for this phase**: the resolver already ignores every screen except the one built-in notched display, so an external monitor's resolution changes never feed into this calculation at all. |
| "Did settings change, re-render" plumbing | A new `Equatable` "AppliedScale" struct + re-host call (mirroring `AppliedTheme`) | The existing `handleSettingsChanged()` → `updateVisibility()` pipeline, plus plain `@AppStorage` at Site 1 | `AppliedTheme`'s re-host mechanism exists for controller-owned derived state (accent Int → Color, material String → enum) that must be pushed via `@Environment`. Scale has no such controller-side derivation the View can't already do itself (Pattern 4) — adding a parallel mechanism duplicates existing, working machinery for no benefit. |
| Percent/value clamping for corrupted `UserDefaults` | Ad-hoc `min(max(...))` scattered per call site | One shared clamp inside the pure `resolvedIslandScale(...)` function (Pattern 2) | Every other enum-backed setting in this file (`WeatherStyle`, `SwitcherLayout`) funnels a possibly-corrupted stored value through exactly one `?? .default` fallback site — the same discipline applies here: one shared clamp, not N ad-hoc ones. |

**Key insight:** This phase's entire risk surface is architectural discipline (touching all 3 geometry sites consistently), not missing tooling — every primitive needed (pure functions, `@AppStorage`, `NSScreen` bridging, the settings-apply pipeline) already exists and is proven in this exact codebase.

## Common Pitfalls

### Pitfall 1: Depth-scaling `cameraClearance` below the physical camera safe zone
**What goes wrong:** If the 80%-floor depth slider multiplies through the same `cameraClearance` (42pt) constant used to keep expanded content clear of the physical camera housing, dragging Depth to 80% shrinks that clearance to 33.6pt — potentially re-introducing the exact "title renders under the camera" bug `cameraClearance` was created to fix (see its own doc comment history, Phase 28-30 gap-closures).
**Why it happens:** `cameraClearance` is a *hardware-safety* constant masquerading as a *content-layout* constant — it lives in the same file and reads like just another spacing number, but its real purpose (clearing a fixed physical feature) doesn't scale with the user's chosen content size.
**How to avoid:** Exclude `cameraClearance` from the depth-scale multiplication entirely (treat it like `collapsedSize`, D-02's precedent) — apply depth scale only to the *content* height that sits below the clearance, not to the clearance itself. Flag this explicitly for user/planner confirmation since CONTEXT.md's canonical_refs constant list did not call this constant out either way.
**Warning signs:** On-device UAT at 80% depth showing clipped title text or a title rendering partially under the notch camera on Home/Weather/Calendar tabs.

### Pitfall 2: Scope ambiguity — 6 named views vs. ~14 actual expanded/HUD surfaces sharing the same constants
**What goes wrong:** D-01 enumerates exactly 6 views (Home, Tray, Weather, Calendar, Quick Actions, Switcher). The codebase has at least 8 more surfaces built on the identical fixed-pt pattern that are NOT named: Timer/Pomodoro setup (`timerSetupContentHeight`), the Output-panel (`outputPanelExtraHeight`), Onboarding (`onboardingSize`), and the various transient wings (Charging/Device/Focus/CapsLock/Meeting/Download/Update — all share `wingsSize`/`wingsLabelWidth`). If only the 6 named views scale, the app will look visually inconsistent (some tabs get bigger with the slider, others don't) the very next time the user visits Timer or triggers a Meeting HUD after cranking the sliders.
**Why it happens:** CONTEXT.md's discussion was scoped around the specific complaint (Home content too small after a resolution change) and named the tabs the user actually compared, not an exhaustive inventory of every `NotchPillView` presentation.
**How to avoid:** Planner should explicitly decide (ideally re-confirm with the user, since it changes visible scope) whether Timer/Meeting/Onboarding/wings also scale, or are deliberately excluded like the collapsed pill (D-02). Either answer is defensible; leaving it implicit is not.
**Warning signs:** A plan that touches only the 5 constants literally named in canonical_refs (`expandedSize`, `traySize`, `calendarWidth`, `weatherMediumContentHeight`/`weatherLargeContentHeight`, `quickActionsBarContentHeight`) without an explicit decision on the rest.

### Pitfall 3: Panel-frame reservation must upper-bound at 150%, not the CURRENT scale
**What goes wrong:** `positionAndShow()` (Site 2) already follows a "reserve for the worst case, up front, never live-resize" convention (e.g. unconditionally reserving `weatherLargeContentHeight` even when Medium is showing). If the new scaled reservation instead reserves for the CURRENT slider value only, then live-dragging the Width/Depth sliders from e.g. 100% up to 150% would need the panel window itself to grow WHILE already expanded/interactive — a live window resize mid-interaction, which is exactly the class of bug this file's entire union-of-static-frames design exists to avoid (per its own extensive doc comments on Phase 20/26/32/48).
**Why it happens:** It's tempting to compute the panel frame reservation using `resolvedIslandScale(...)`'s live value, mirroring how the CONTENT (Site 1) legitimately does scale live.
**How to avoid:** Reserve Site 2's panel frame using the fixed upper bound (constant × 1.5, D-04's max), exactly like the existing `weatherLargeContentHeight`-always-reserved convention — never the live current-scale value. Site 1's rendered content and Site 3's click-through rect DO use the live current scale (they're not pre-reserved unions, they're computed per-presentation); only Site 2's panel-frame union needs the worst-case constant.
**Warning signs:** The panel visibly clips or jumps when a slider is dragged past whatever value was live when the panel was last shown.

### Pitfall 4: `traySize`/`calendarWidth` are WIDTH-only constants; most others are HEIGHT-only — don't apply both axes to every constant
**What goes wrong:** `traySize` is a `CGSize` but only `.width` is ever read (the file's own comment says `.height` "is never read" — Tray's real height comes from `trayContentHeight`). Applying `depthScale` to `traySize.height` would be a no-op that gives false confidence the depth axis is wired for Tray, when the real height constant (`trayContentHeight`) was never touched.
**Why it happens:** Skimming `CGSize`-typed constants and assuming both dimensions are "the" width/height for that view, rather than checking which field is actually consumed at the render site.
**How to avoid:** Build an explicit width-axis-vs-depth-axis constant inventory before touching call sites (this research's Architecture Patterns / Recommended Project Structure section lists the exact constants; verify each one's actual consumer, not just its declared type) — several are asymmetric (`traySize.width` used, `.height` unused; `calendarWidth` is a bare `CGFloat`, not a `CGSize`, paired with the separately-named `calendarContentHeight`).
**Warning signs:** Tray or Calendar visibly not resizing on one axis while Home/Weather do.

## Code Examples

### Full auto+manual resolution, matching the codebase's existing pure-function style

```swift
// Source: pattern matches Islet/Notch/NotchGeometry.swift's existing hasNotch/notchSize contract
// (read verbatim 2026-07-26) — no live NSScreen dependency, fully unit-testable.

// D-06: locked baseline where today's fixed-pt constants read correctly.
func islandAutoScaleFactor(screenWidthPoints: CGFloat, baseline: CGFloat = 1470) -> CGFloat {
    guard baseline > 0, screenWidthPoints > 0 else { return 1.0 }
    return screenWidthPoints / baseline
}

// D-04: 80%-150% floor/ceiling applies to the EFFECTIVE (auto + manual) value, not the
// raw stored offset — so a corrupted/extreme stored offset can never push the rendered
// island outside the locked slider range, matching this file's existing defensive-clamp
// convention (e.g. ActivitySettings.accent(for:) clamping an out-of-range palette index).
func resolvedIslandScale(auto: CGFloat, manualOffset: CGFloat, range: ClosedRange<CGFloat> = 0.8...1.5) -> CGFloat {
    min(max(auto + manualOffset, range.lowerBound), range.upperBound)
}
```

## Open Questions

1. **Does D-01's "Switcher" mean only `switcherRowHeight` (44pt), or also the nav-circle-button glyph sizes inside it?**
   - What we know: `switcherRowHeight` is the row's reserved height; the buttons inside (`navCircleButton`) have their own icon-size constants not enumerated anywhere in CONTEXT.md.
   - What's unclear: Whether "Switcher" scaling means just the row's height (so buttons get more breathing room) or the buttons themselves grow too.
   - Recommendation: Default to scaling only the row height/width envelope (simpler, lower risk of icon-density/alignment bugs), leave button glyph size fixed unless UAT flags it as visually inconsistent — flag for discuss-phase or UAT round if ambiguous.

2. **Should the two manual sliders' Settings-window labels show a percentage (matching the UI-spec's `"NNN%"` mock) computed from the EFFECTIVE (auto+offset) value, or from the raw stored offset?**
   - What we know: 67.1-UI-SPEC.md locks the visual format (`Text("\(Int(widthScale * 100))%")`, `.monospacedDigit()`).
   - What's unclear: `widthScale` in the UI-spec's pseudocode is presented as if it's a single bound value already in the 0.8–1.5 range — this research recommends that binding be a COMPUTED (auto+offset) Binding, not the raw `@AppStorage` value directly, which the UI-spec's simplified pseudocode doesn't distinguish.
   - Recommendation: Planner should make the Slider's `Binding<Double>` a computed binding (get: `resolvedIslandScale(auto:offset:)`, set: `offset = newValue - auto`) rather than binding the raw `@AppStorage` property directly — the UI-spec's visual/copy contract is unaffected either way, this is purely a data-plumbing detail.
