Two related fixes to the collapsed-state "Live Activity" wings (Now Playing / Charging /
Device / OSD-Brightness / OSD-Volume / Caps Lock / Update / Download / Timer / Meeting — every
`wingsShape()`-based glance in `NotchPillView.swift`):

**Fix #1 (root cause, no new tuner needed):** `resumePreviewWings(_:)` — the idle-hover
"resume last-played track" preview that appears when the user hovers the collapsed island
after music has stopped — is the ONE wing that was never converted to this codebase's
established camera-safe, resolution-aware wing formula. It still renders at the raw, hardcoded
`Self.wingsSize` constant (290x32pt) via a plain `Spacer()`-based `HStack`, so it never
recomputes when the screen resolution changes and is completely disconnected from BOTH existing
manual overrides (Settings > Island Size Width/Depth sliders, and the DEBUG Wing Tuner menu) —
exactly matching the user's report ("Ich kann mit dem Margin und so das leider nicht
einstellen") and the on-device hypothesis that the view itself doesn't grow with resolution.
Every sibling wing (charging, device, focus, osd, capsLock, meeting, and even this wing's own
live-playing counterpart `mediaWingsOrToast`) was already converted to the
`rawNotchHalfWidth`+`margin`->`cameraBlockWidth`, `resolvedWingWidthScale`/
`resolvedWingDepthScale`-scaled, `wingsShape(leftWidth:rightWidth:depthScale:)` pattern in
earlier phases (67.1-08/67.1-09/67.1-10, quick tasks 260729-*). Task 1 applies that exact,
already-proven pattern to `resumePreviewWings` — the root-cause fix. Once wired in, this wing
automatically (a) recomputes live on every `didChangeScreenParametersNotification` (resolution
change, the same mechanism every other wing already uses — no new observer needed) and (b)
becomes controllable via the EXISTING production "Island Size" Width/Depth sliders in Settings
AND the existing DEBUG Wing Tuner menu's Leading/Trailing/Margin nudges — zero new
UserDefaults keys, zero new UI.

**Fix #2 (new manual tuner, additive/separate from Width-axis controls):** the DEBUG Wing
Tuner menu (`AppDelegate.swift`, quick task 260728-wg7) currently has 5 nudge axes — Leading,
Trailing, Margin, Gap, Corner Radius — all on the WIDTH/horizontal axis (plus the
Settings-facing "Island Size" Depth slider, which is a coarse *proportional* 80%-150% scale
applied to every dimension at once). There is no fine, *additive*, vertical-only control for
"how far the wing's black shape extends downward" — exactly what the user asked for, separate
from the width/margin controls they already have. Task 2 adds a 6th Wing Tuner nudge axis,
`heightNudge`, wired into the TWO canonical shared wing-height sites (`wingsShape`'s own
`size.height` and `mediaWingsOrToast`'s own inline height calc) — the single choke point every
`wingsShape()`-based wing (now including the fixed `resumePreviewWings` from Task 1) and the
live media wing route through, so ONE new nudge covers every Live Activity (Music, Charging,
Device, Brightness/Volume OSD, Caps Lock, Update, Download, Timer, Meeting) in one shot,
mirroring the exact mechanism/menu/reset/print conventions Wing Tuner already established.

Purpose: stop the collapsed-island resume-preview from silently drifting out of alignment on
resolution changes (root cause, not a band-aid), and give the user a genuinely separate,
fine-grained manual "how far down" control for every Live Activity wing, reusing 100% of this
codebase's existing debug-tuner infrastructure and workflow (live-nudge -> note the printed
delta -> bake into source -> reset).
Output: `Islet/ActivitySettings.swift` (1 new DEBUG-only key), `Islet/Notch/NotchPillView.swift`
(`resumePreviewWings` rewritten to the shared wing formula; 1 new DEBUG-only `@AppStorage` +
always-compiled nudge property; `wingHeightNudge` wired into the 2 shared height sites),
`Islet/AppDelegate.swift` (4 new Height nudge menu actions + Reset/Print updated). Zero effect
on Release builds (`#if DEBUG` throughout, matching this project's own convention).
